# 종목별 실시간 RAG 매매 파이프라인 — 현재 엔진 대조 검토 (2026-10-18)

> 기준 소스: main `d0cc71a` (PR #183 병합 직후). 운영 `161b394` · KR 신규 매수 중지 · 월 USD 100 예산 · 10월14일 단발 관측 예약은 이 검토와 무관하게 불변이다.
> 이 문서는 **분석 기록**이다. 코드·설정·운영·예약 변경은 없다.

## 0. 결론

사용자가 제시한 "원천 → 티커 분배기 → 종목별 독립 큐 → 실시간 RAG + LLM 판단 → 즉시 주문" 구조는 **전체를 들여오지 않는다.** 가져올 것은 두 조각 — **수집 시점의 종목 태깅·원천 시각 저장(분배기의 색인 기능)** 과 **LLM 2차 검증의 검색 맥락 확장(오프라인 비교 후 승격)** — 이고, 둘 다 주문 경로를 바꾸지 않는다.

변형 가정 두 가지의 답:

| 가정 | 풀리는 것 | 안 풀리는 것 | 의견 |
|---|---|---|---|
| 로컬 PC(RTX 5080 16GB + RAM 64GB)에서 실행 | LLM 지연·호출 비용, 메모리(OOM), 벡터 색인 용량 | KIS appkey당 1세션·등록 41건·REST 합산 한도, 한 계좌 두 프로세스의 중복 주문 위험, 회전·수수료 구조, 측정 기준선 공백, 뉴스 선행성 | **라이브 2호기 금지. 오프라인 재생·모델 비교·수집기 호스트로 사용** |
| KIS + 토스 API 병렬 집계 | 관측 폭 41 → 최대 +100종목(체결+호가 기준), 후보 관측 분모 확대, 원천 교차 확인 | 실행 가격은 여전히 KIS KRX 단일, 토스 KRX+NXT·LOSSY 가격의 KIS 재표기 금지, 자료 폭 자체는 병목이 아님, grant 만료·약관/소유권 재확인 | **"병렬 판단"이 아닌 "병렬 관측"으로 찬성 — 새 grant·한정 후보·유한 용량** |

## 1. 검토 대상 구조 (사용자 제시 요약)

1. 원천: 뉴스 피드, 공시(DART/SEC), 시세(호가·체결·분봉).
2. 티커 분배기: 텍스트에서 종목코드를 추출해 종목별 채널로 포워딩, 다종목 뉴스는 멀티캐스트.
3. 종목별 독립 파이프라인: 유입 텍스트 임베딩 → 종목 히스토리(실적·테마·산업 보고서) 검색 결합 → LLM + 정량 지표 판단 → BUY/SELL/HOLD, 0.1초 이내.
4. 실행 레이어: 신호 즉시 증권사 API 주문.
5. 제시된 트레이드오프: 종목 수에 비례하는 상시 가동 비용(서버리스 스케일링 제안), 거대 LLM 지연(1B~8B sLLM 로컬 GPU 서빙 제안).

## 3. 강점 — 우리에게 실제로 의미 있는 것

1. **종목 태깅을 수집 시점에 하는 것.** 뉴스·공시·텔레그램 글에 종목코드와 원천 게시 시각·수집 시각을 붙여 저장하면 "이 판단이 어떤 정보를 언제 받았는가"를 사후 재생할 수 있다. 64차 판단 기록이 못 채우는 `source_observed_at`을 메운다. LLM 비용 0.
2. **후보 종목 공시 감시.** 지금은 보유 종목만 본다. 후보가 신호를 내기 직전에 유상증자 등 위험 공시가 떴는지 게이트가 모른다. 이는 진입보다 **거절 근거**로 가치가 있다 — 회전을 늘리지 않는 방향이다.
3. **검색 맥락 확장 가능성.** `query_symbol` 600자에 최근 공시 제목·과거 실적 발표일 전후 가격 반응을 더하면 LLM 입력이 풍부해질 수 있다. 단 64차 기록으로 같은 입력에 "맥락 있음/없음" 판정을 오프라인 비교한 뒤에만 켠다.

## 4. 약점 — 적용을 막는 것

1. **인프라 상한이 구조와 충돌한다.** KIS 공식 공지(2026-04-20): appkey당 1세션, 실시간 등록 합산 41건(`src/data/feeds/quote_subscription.py:3`, `kis_websocket.py:115` `MAX_SUBSCRIPTIONS=40`). "수백 종목 전용 실시간 파이프라인"은 이 브로커로 만들 수 없다. 운영 서버는 RAM 3.8GB(09-29 OOM 사망 이력), GPU 없음.
2. **빠른 반응은 손실 구조를 키운다.** 9월 리뷰: 연환산 91배 회전이 이익의 43%를 수수료로 반납, 건당 기대값(-5,213원)이 건당 수수료(5,065원)와 같은 크기(`docs/reviews/strategy-architecture-review-2026-09.md` §1~2). 실거래 KODEX200 초과수익은 포지션당 −1.66%(t=−3.98). 처방은 "더하는 것이 아니라 빼는 것"이었다. 뉴스 반응을 빠르게 하는 구조는 회전을 늘린다.
3. **멀티캐스트는 상관 진입을 만든다.** "반도체 호재" 1건이 10개 파이프라인에 동시에 들어가면 같은 뉴스로 같은 방향 주문이 여러 건 난다. 섹터 한도는 있지만 한 뉴스에 묶인 상관 위험을 한 번에 진다.
4. **LLM 예산이 안 맞는다.** 월 USD 100·80/95/100% 절약 정책(`config/default.yml:18`). 종목별·뉴스별 호출은 하루 수십~수백 건이 된다. 지금은 신호 1건당 Bull/Bear 2~3회다.
5. **측정이 안 되는 상태에서 판단 원천을 추가한다.** 계좌 기준선 결측으로 TWR null(`docs/operations/account-baseline-status-2026-10-13.md`), 현재 LLM 판단의 순효과도 미측정. 여기에 뉴스 RAG 판단을 얹으면 어느 쪽이 성과를 냈는지 분리할 수 없다. 사용자 승인 순서(버전 확정 → 계좌 측정 → 선정·진입·청산 분해 → 새 가설)에서 이 제안은 맨 마지막이다.
6. **원천의 선행성이 입증되지 않았다.** 10-13 확인한 텔레그램 채널(growthresearch)은 30건 중 28건이 이미 보도된 기사 재게시(시간당 약 1.2건), 네이버 뉴스는 이미 수집 중이다. "뉴스가 뜨면"의 뉴스가 시장보다 먼저 오는지 자료가 없다. H1~H3 가설은 전부 기각 상태다.

## 5. 변형 가정 A — 로컬 PC(RTX 5080 16GB VRAM + RAM 64GB)에서 실행하면

### 5-1. 하드웨어로 풀리는 것

| 제약 | 운영 서버(현재) | 로컬 PC | 비고 |
|---|---|---|---|
| LLM 지연 | 클라우드 호출, 폴백 타임아웃 10초 | 7~8B 모델 4bit 양자화 시 VRAM 약 5~6GB, 14B 4bit 약 9~10GB. 32B 4bit(약 18~20GB)는 16GB에 안 들어간다 | 생성형 판단(200토큰 내외)은 **수백 ms~수 초**가 현실적 추정이며 실측 필요. 0.1초는 분류·임베딩에만 해당 |
| LLM 호출 비용 | 월 USD 100 원장 | 전기료 외 한계비용 ≈ 0 | 호출 수 제약이 사라지므로 **판단 횟수 상한을 설정으로 따로 둬야** 회전이 폭주하지 않는다 |
| 메모리 | 3.8GB, OOM 이력 | 64GB | 전 상장 종목(약 2,700개) 문서·임베딩 색인을 메모리에 올릴 수 있다. Kafka 불필요, asyncio + SQLite/FAISS로 충분 |
| 임베딩·검색 | 없음 | bge-m3·multilingual-e5 급 임베딩은 GPU에서 ms 단위 | RAG의 "검색" 부분은 로컬에서 실시간이 된다 |

한국어 금융 텍스트 후보 모델(EXAONE 3.5 7.8B, Qwen3 8B, Kanana, HyperCLOVA X SEED 등)은 **매매 판단 품질이 미검증**이다. 64차 판단 기록(같은 공통 입력·같은 역할 프롬프트)을 재생해 클라우드 모델과 판정 일치율·근거 품질을 비교하는 것이 첫 실험이며, 이 비교는 68차가 예정한 "동일 입력 모델 비교" 단계와 정확히 같다.

### 5-2. 하드웨어로 안 풀리는 것

1. **KIS 세션·한도는 계좌/appkey에 묶인다.** 로컬에서 실시간 WS를 열면 운영 서버의 WS 세션과 충돌한다(appkey당 1세션). REST 초당 한도(EGW00201)와 원장 TR 계좌당 초당 1건(EGW00215)도 두 호스트가 합산해서 쓴다. 토큰 재발급 1분 제한(EGW00133)도 공유된다. 현재 운영은 단일 appkey이며 복수 발급 가능 여부는 미확인이다.
2. **한 계좌에 두 프로세스는 중복 주문 위험이다.** 싱글톤 락(`src/utils/trader_lock.py`)과 "봇 실행 중 주문 CLI 거부"는 **같은 호스트 안에서만** 유효하다. 로컬 봇과 서버 봇이 같은 종목에 동시에 주문하면 막을 장치가 없다. pending·현금 예약·실행 원장도 호스트별로 따로 돌아 대사가 깨진다.
3. **회전·수수료·상관 진입·기준선 공백·원천 선행성(§4의 2·3·5·6)은 하드웨어와 무관하다.** GPU는 "빠르고 싸게 판단"을 가능하게 할 뿐, 그 판단이 비용 후 수익을 내는지는 바꾸지 않는다.
4. **운영 전체를 로컬로 옮기는 안**은 별개 문제다. 가정 전원·네트워크·OS 재부팅이 장중 손절·보유 관리를 끊을 수 있다. 현재 systemd 자동 재시작·OOM 보호·예약 관측 체계를 버리는 대가가 GPU 하나보다 크다.

### 5-3. 로컬 PC의 적정 역할

- **오프라인 재생기:** 64차 `llm_decisions/decisions-YYYY-MM.jsonl` 과 H1 20일 관측 자료를 입력으로, 로컬 sLLM·검색 맥락 유무·역할 프롬프트 변형을 같은 입력에서 비교한다. KIS 호출 0, 주문 0.
- **수집기 호스트:** 텔레그램 채널·뉴스·DART 후보 공시의 종목 태깅 수집(§7 ①)은 KIS와 무관하므로 로컬에서 돌려도 운영과 충돌하지 않는다. 다만 수집 결과를 운영 봇이 읽으려면 파일/DB 전달 경로가 필요하다.
- **금지:** 운영 계좌로 실시간 WS·주문을 내는 2호기.

## 6. 변형 가정 B — KIS API + 토스 API 병렬 집계

### 6-1. 저장소에 기록된 토스 사실 (22·26·38·40차)

- 공식 AsyncAPI 1.2.2: 국내 실시간 체결/호가, **연결당 100구독·계정당 2연결**, 구독 단위는 채널×종목(같은 종목 체결+호가 = 2구독)(`docs/research/current-engine-selection-entry-protocol-2026-09-30.md` 22차).
- 호가는 **KRX+NXT 통합**이며 거래소별 가격/잔량 구분 필드가 없다. 지연 시 중간 메시지 **유실 가능(LOSSY)**, 유실 검출 sequence 없음, 구독 직후 초기 snapshot 없음, 데이터 시각 null 가능.
- 기존 계약: 토스 프레임을 KIS 비교기에 이름만 바꿔 넣지 않는다. 토스 가격은 통합 시세 대리치이지 KIS에서 그 가격에 체결 가능하다는 증거가 아니다.
- 주문·청산·사이징·계좌·잔고는 **KIS 단독**(설계 결정, 변경 없음).
- 운영 상태: 승인 grant 09-22 18:00 만료, `qwq-toss-observer.service` 퇴역(disabled/inactive), 원장 `/var/lib/qwq-toss-observer` 보존. 재가동은 **새 grant + 약관·자료 보존 허가·자격 소유권·허용 host/IP·승인 기간**을 다시 확인해야 한다(`docs/operations/toss-shadow-runtime.md`). 10-02 실측에서 10,000 프레임 상한으로 09:24 조기 종료했고 이후 cap 50,000 검증이 이뤄졌다.

### 6-2. 병렬 집계로 얻는 것

1. **관측 폭.** KIS 41건 + 토스 최대 200구독(체결+호가 동시면 100종목). 후보 관측 분모가 커진다 — 지금 H1 관측은 order_ready 최초 5개에만 호가를 배정한다(65차).
2. **원천 교차 확인.** 같은 종목을 두 원천에서 받으면 KIS 프레임 결손·지연을 감지할 수 있다. 단 토스가 LOSSY라 토스를 기준으로 삼지는 못하고, "양쪽 모두 수신"만 신뢰 구간으로 쓴다.
3. **이 확장은 §7의 재검토 조건("뉴스 도달 → 첫 호가" 비용 후 차이)에 정확히 필요한 자료다.** 측정 단계의 도구로서 가치가 있다.

### 6-3. 병렬 집계로 얻지 못하는 것

1. 실행 가격은 여전히 KIS KRX 하나다. 관측이 넓어져도 체결 가능 가격은 늘지 않는다.
2. 자료 폭은 병목이 아니다. 후보가 늘면 거래가 늘고, 선정이 그대로면 수수료만 는다(§4-2).
3. 토스 측 처리량·수신 안정성·비용 우위는 미측정이다(22차). 1회 실측은 상한 조기 종료로 불완전했다.
4. 두 원천의 시장 기준(KRX vs KRX+NXT)이 달라 하나의 가격 비교기에 섞을 수 없다. 혼합 효과를 별도 표시하는 평가 계약이 필요하다.

### 6-4. 적정 구조

22차 추천과 같다 — **토스는 후보 관측 전용 독립 수집기(별도 OAuth client_id·별도 서비스·별도 원장), KIS는 진입 가격·주문·체결 근거.** 두 자료는 같은 후보 ID·판단 시각으로 **오프라인 조인**한다. "토스 신호로 KIS 주문"은 하지 않는다. 시작은 유한 후보·유한 용량(예: 하루 후보 ≤ 20종목·프레임 cap 명시)이며 100구독을 한꺼번에 채우는 결정이 아니다.

## 7. 종합 의견과 적용 순서

**전체 구조는 지금 적용하지 않는다.** 구조가 손실 원인(회전)을 키우는 방향이고(§4-2), 효과를 측정할 기준선이 아직 없다(§4-5). 인프라 상한(§4-1)과 예산(§4-4)은 그 전에 물리적으로 막는다. 로컬 GPU는 §4-1·§4-4를 일부 풀지만 §4-2·3·5·6은 그대로다. 토스 병렬은 측정 폭을 넓히지만 판단·실행 구조를 바꾸지 않는다.

가져올 조각 (순서대로, 전부 주문 경로 불변):

| 순서 | 조각 | 비용 | 바꾸는 것 | 로컬/토스 역할 |
|---|---|---|---|---|
| ① | 뉴스·공시·텔레그램 **종목 태깅 + 원천 시각 저장**(분배기 = 저장 단계 색인) | LLM 0, 코드 소규모 | 64차 `source_observed_at` 공백을 메움. 텔레그램 A안(수집만)과 같은 작업으로 묶임 | 로컬 PC가 수집기 호스트 가능 |
| ② | 후보 종목 DART 위험 공시를 **게이트 거절 근거**로 추가 | DART 호출 소폭 증가(한도 20,000/일 안) | 진입 억제 방향. `signal_events` G-게이트 추적에 사유가 남아 효과 측정 가능 | — |
| ③ | `query_symbol` 맥락 확장을 **오프라인 재생으로만** 비교 | 오프라인 실험분만 | 64차 기록으로 같은 입력에 맥락 유무 판정 차이를 본 뒤 승격 여부 결정 | 로컬 GPU로 sLLM·임베딩 포함 비교 |
| ④ | 토스 **관측 전용** 재가동(새 grant·유한 후보) | grant·약관 재확인, 수집 서비스 | H1 관측 분모 확대, "뉴스 도달 → 첫 호가" 쌍 확보 | 토스 병렬 집계의 자리 |

**재검토 조건:** ①·④가 쌓인 뒤, 뉴스 도달 시각과 첫 호가를 맞춰 **비용 후** 양의 차이가 실제 후보군에서 통계적으로 나오면(기준은 기존 H1 계약처럼 사전 고정), 그때 "기존 후보에 한해 공시/뉴스 도달 시 재채점"을 기존 SIGNAL → 게이트 → ORDER 경로 **안에서** 한정 적용하는 것을 다시 본다. Kafka·종목별 워커·뉴스 직결 주문·운영 계좌 로컬 2호기는 그 뒤에도 필요 없다.

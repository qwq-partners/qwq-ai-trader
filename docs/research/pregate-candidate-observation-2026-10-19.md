# 시장 방어 이전 후보의 가격 관측

## 목적과 범위

10월19일 v5는 반환 후보 41건이 모두 시장 방어에서 멈췄고, 후보 호가는
없었다. 다음에는 시장 방어를 완화하기 전에, 첫 스캔의 관측 대상 후보가
이후 어떻게 움직였는지 확인한다. 좋은 종목을 차단했는지와 손실을 피했는지
분리할 자료를 만드는 단계이며, 실거래 수익 개선의 증명은 아니다.

최초 PR #226은 **오프라인 자원 점검과 가격 판독**이다. 후속 메모리/유량 구현은 아래 후속 절을 따른다. 기존
`runner-first-scan-v4`가 남기는 자료를 사용하며, 수집기·주문·시장 방어·설정·
배포·예약은 변경하지 않는다. 날짜가 정해진 설치 파일을 만들지 않는다.

## 고정 계약

- 첫 반환 스캔 한 번만 대상으로 한다. 첫 스캔이 비었어도 다음 스캔으로
  대체하지 않는다. 반환 후보 전체가 분모다.
- 반환 순서 상위 5종목이 고정 관측 대상이다. 6위 이후는 의도적 비구독,
  상위 5개 중 실제 배정 실패는 별도 상태다. 전자를 유효 관측으로 세지 않는다.
- BOOK·체결 상태·장운영 상태 3채널로 최대 15건을 추가한다. 운영 구독,
  외부 사용, 예비 용량을 합해 실제 상한을 넘을 수 없다.
- 엄격히 검증된 저널과 study 지문·epoch·스캔 범위·선정/게이트/프레임
  계약을 대조한다. 봉인 미완료·누락·시간 역행을 성공으로 승격하지 않는다.
- 후보 확정과 구독 배정 이후의 **첫 KRX BOOK**을 기준 호가로 선택한다.
  첫 호가가 불량해도 뒤의 좋은 호가로 교체하지 않는다. 기준은 실제 주문이나
  LLM 판단이 아니라 관측 기준점이다.
- 기준 호가 관측 시각에서 900초 뒤 처음 수신한 KRX BOOK을 후속 호가로
  선택한다. 허용 지연은 5초다. 관측 종료 전 성숙 시간이 부족한 경우를
  호가 부재와 구분한다. 미래 호가는 분석 시각 이후에서 가져오지 않는다.
- 장 상태는 호가와 같은 연결·세대이고 호가보다 먼저 수신한 값만 사용한다.
  같은 수신 시각, 오래된 값, 채널 부재, VI 무사건은 정상시장 증거가 아니다.
  기존 분류기를 재사용하며 거래소 날짜/시각을 합성하지 않는다.
- 실제 가격과 상태·결측 사유를 출력하되 체결 가능성·계좌 수익·수익성 통과는
  주장하지 않는다. `account_return=null`, `profitability_pass=false`,
  `production_eligible=false`를 유지한다. 비용·수량·체결을 지어내지 않는다.

## 자원 점검과 설치 전 남은 조건

기존 first-scan-v4의 기본 계약에는 LLM 관측 전용 512MiB 메모리 보호가 적용되지 않는다.
후속 구현에서는 명시 `record_allocations`를 추가한 v4에 한해 같은 보호를 적용한다.
장 상태를 켠 경우 버퍼당 최대 레코드 크기로 계산한 저널 예산은 크게 늘고,
기존 통합 판독은 256MiB 한도가 있다. 점검 도구는 요구량과 각 검사 결과를
보여주며, 설정 숫자만 맞는다고 설치 가능으로 표시하지 않는다.

최소 산술에는 선정/게이트 전체 분모, 기준·후속 BOOK 10건, 두 시점의 두 상태
채널 20건, 한 연결의 후보 구독 수명주기와 운영 채널 수명주기를 포함한다.
첫 연결의 이 최소 시나리오를 통과해도 지속 시세·재연결·운영 이벤트 유량을
감당한다는 뜻은 아니다. `record_volume_qualified=false`를 별도로 유지한다.

전용 메모리 보호·종류별 저장 한도와 합성 유량 검증은 아래 후속 절에서 구현한다.
실제 설치 전에는 준비 상태 검증, 실제 구독 수요/유량 확인, 소비된 v5 요청과
drop-in의 안전한 교체가 남는다. 날짜와
휴장일 확인도 그 단계에서 고정한다. 기존 LLM 판독기는 그대로 유지한다.

## 구현과 사용

- `scripts/assess_pregate_capture.py`: 명시한 study와 운영/외부 등록 수로 자원
  산술을 계산한다. 실제 운영 수요를 조회하지 않고 설치 파일도 만들지 않는다.
- `scripts/report_pregate_candidate_observation.py`: 검증된 봉인 원장과 같은 study로
  전체 반환 후보의 배정·기준/900초 호가·각 시점 장 상태·선정/차단 근거를 출력한다.
  불량 첫 호가를 뒤의 좋은 호가로 대체하지 않는다.

```bash
python scripts/assess_pregate_capture.py /private/study.json \
  --operational-registrations 16 --external-registrations 0
python scripts/report_pregate_candidate_observation.py \
  --study /private/study.json --journal /private/engine.jsonl \
  --as-of '<실제 분석 시각, 시간대 포함>' --max-journal-bytes 268435456
```

위 등록 수는 사용 예이며 현재 수요 확인값이 아니다. 10월19일 v5는 LLM-window
형식이므로 이 새 판독기에 넣지 않는다. 기존 v5 실측 결과를 다시 계산하거나
후보 호가가 있었던 것으로 바꾸지 않았다.

## 남은 순서

1. 명시된 first-scan 보유 메모리 보호·종류별 개수/바이트 예산과 합성 생산 경로 검증은
   아래 후속 절에서 완료한다. 실시장 유량·프로세스 전체 RSS 보장으로 해석하지 않는다.
2. 첫 스캔의 준비 상태 판정과 소비된 v5 요청/drop-in의 소유권을 확인하는
   교체 절차를 구현·독립 리뷰한다. 과거 미소비 요청용 wrapper를 이어붙이지 않는다.
3. 그 뒤 거래일·운영 버전·현재 구독 수요를 확인하여 짧은 단발 관측을 설치한다.
   자료가 생기면 일별 누적으로 차단 후보 가격을 분석하고, 비용·실제 진입/청산
   자료가 갖춰졌을 때 순수익 개선 여부를 평가한다.


## 후속 PLAN — 첫 스캔의 메모리 보호와 저장·판독 한도

첫 스캔 후보가 시장 방어에서 차단되더라도 가격을 수집하려면 봇 메모리와
판독 범위 안에서 관측이 끝나야 한다. 기본 계약은 보존하고 다음 두 설정을
명시한 `runner-first-scan-v4`만 확장한다. 거래 신호·시장 방어·LLM 정책은 바꾸지 않는다.

- `record_allocations`: 양의 정수 `ws_quote`, `market_state`, `other`.
  `scan_metadata`는 `1 + 선정 후보 상한 + 게이트 후보 상한`으로 계산한다.
  장 상태 몫은 `channels.market_state_max_records`와 정확히 같아야 한다.
- `record_max_bytes`: 선택 필드이며 위 할당과 함께만 허용한다. 네 종류의
  직렬화 최대 바이트를 명시하며 `scan_metadata`는 전체 레코드 상한과 같아야 한다.
  종류별 크기 설정이 없으면 기존의 균일 최대 크기 계산을 유지한다.
- 보유 레코드 트리의 보수적 합계는 512MiB로 제한한다. 이 한도는 전체
  프로세스 RSS, 임시 직렬화·큐·별도 판독 프로세스의 메모리 상한이 아니다.
- 종류별 개수/크기 거부는 복사·원장 전달·후보 등록·할당 계수 변경 전에 처리한다.
  누락과 불완전 사유를 보존하고, 기존 운영 시세 콜백을 중단하지 않는다.
- 종류별 크기를 쓸 때만 `Σ[종류별 개수 × (종류별 최대 바이트 + 2048)] + 2048`을
  저널 상한의 최소값으로 쓴다. 실제 sequence와 보강된 스캔 필드까지 포함한
  UTF-8 직렬화 크기를 검사하며, 오프라인 재생도 같은 개수/크기 한도를 검사한다.

## 후속 DO — 구현과 합성 유량

`first_scan_resources.py`의 공통 계약을 설치 검증·버퍼·재생·자원 점검에서
사용한다. `EntryObservationBuffer`의 기존 보유 메모리 검사를 재사용하며,
LLM 입장 처리와 첫 스캔의 기록 예산을 분리했다. 새 계약이 없는 과거 v4,
기존 LLM 및 다른 관측 형식의 동작을 유지한다.

합성 부하는 [10월14일 파일럿](market-state-pilot-readout-2026-10-14.md)의 5분간
한 종목 BOOK903·체결 상태856건을 참고한 약3Hz 시나리오다. 5종목의 BOOK과
체결 상태를 각각 초당3건씩 1,205회 주입하고 운영 종목1개의 두 채널도 유지한다.
실제 파일럿의 장운영 채널은0건이었으므로, 시험의 장운영10건은 두 기준점의
연결 검증을 위한 **가상 사건**이다. 정상시장 관측 증거로 쓰지 않는다.
새 계약의 수집 창은1,208초, 입장 창300초, 입장 종료 뒤 후미908초다.

| 자원/결과 | 합성 시험 값 |
| --- | --- |
| 반환 후보 / 추가 구독 | 7 / 상위5×3채널=15, 기존 운영2채널 |
| 입력 프레임 / 봉인 레코드 | 38,570 / 37,443 |
| BOOK / 장 상태 | 19,280 / 18,085 |
| 누락 / 기준·900초 후 호가 연결 | 0 / 5종목 |
| 보유 레코드 계측 | 132,761,193바이트, 약126.6MiB |
| 실제 저널 | 약37,044,823바이트, 약35.3MiB; 헤더 시각에 따라 소폭 변동 |
| 종류별 개수 | metadata21 / BOOK22,000 / 상태19,000 / 기타512 |
| 종류별 바이트 | metadata65,536 / 나머지 각4,096 |
| 선언 저널 상한 / 판독 한도 | 256,471,040 / 268,435,456바이트 |

균일65,536바이트 계산은 같은 버퍼에서2,806,968,320바이트를 요구해 판독
한도를 넘었다. 종류별 개수와 실제 직렬화 상한을 함께 강제하여 이 불일치를
해소했다. 작은 실제 파일을 보고 최대 크기 검사를 생략한 것이 아니다.

통합 pytest 프로세스의 관측 peak RSS는 약234MiB였다. 별도 새 판독 프로세스는
1GiB 주소공간 제한 아래37,443건/7후보/5쌍을 읽었고 peak RSS155,956KiB,
6.402초였다(기존30분 선언을 쓴 같은 유량 표본). 이 수치는 해당 합성 자료의
실행 측정이며 상시 운용·최대 payload·돌발 폭주·재연결 유량의 보장이 아니다.

## 후속 SEE — 검증과 적용 범위

- 초기 보호 연결 전7건, 종류별 바이트 계약 전2건의 실패를 재현했다.

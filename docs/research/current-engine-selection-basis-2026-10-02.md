# 종목 선정 점수의 원천 보존과 계산 근거 — 29차

현재 상태: 로컬 구현·독립 재검토·전체 검증 완료. **운영 미배포이며 10월 2일 예약 대상5468208과 설치 입력을 변경하지 않았다.** 이번 수정이 오늘 예약된 수집에 포함된다고 해석하지 않는다.

목표는 여러 정보원을 사용하는 종목 선정이 비용 차감 이익에 도움이 되는지 검증하고, 그 전에 실제 선정 점수를 잘못 만드는 오류를 없애는 것이다. [28차 근거 연결·평가 기준](current-engine-session-evaluation-2026-10-01.md)의 실제 장 상태·청산/계좌 자료 미확보는 계속 남는다.

## Plan — 기록 전에 확인한 점수 오염

`screen_all()`은 최초로 나타난 `ScreenedStock`을 그대로 통합 후보에 넣고 점수에 가중치를 곱했다. 그 객체가 개별 원천 캐시와 공유되면 후속 보정으로 점수·사유·수급 플래그·보조 지표도 캐시에 덮어써졌다. 동일 캐시를 다시 읽는 다음 계산뿐 아니라, 같은 호출 안에서 상승률 자료를 재사용하는 네이버 파생 후보도 영향을 받는다. 최종 통합 캐시도 반환 리스트와 객체를 공유했다.

합성 재현:

- 같은 종목의100점×0.5와60점×0.3에 출현2회 보너스10점을 적용하면78점이다. 기존 코드에서 원천 객체를 다시 사용한 두 번째 계산은67점으로 변했고, 첫 번째 반환 객체도 같은 객체여서67점으로 바뀌었다.
- 네이버 상승률90점에서 파생 점수 `min(90+15,100)`을 계산해야 한다. 기존 경로는 먼저 가중된 점수를 재사용하여 최종53.8점이 됐다. 원천 점수를 보존하면 기존 공식 그대로77점이다.
- 후속 보정에서 붙인 RSI/PER/ATR·사유가 원천 객체에 남고, 반환 리스트를 비우면 통합 캐시도 비는 사례를 재현했다.

이는 합성 조건의 오류 증거다. 실제 운영의 발생 횟수나 손익 영향은 측정하지 않았다. 수급 누적처럼 의도적으로 시간에 따라 바뀌는 보너스는 반복 불변성 테스트에서 분리했다.

선택한 범위는 최초 병합·통합 캐시 저장·폴백 반환의 세 경계에서 깊은 복사를 적용하는 것이다. 공용 캐시 함수나 원천 호출 순서·가중치·선정 필터는 바꾸지 않는다. 관측은 기본 비활성으로, 확인 가능한 계산 항만 기록한다.

## Do — 원점수 보존과 선택적 기록

[스크리너](../../src/signals/screener/kr_screener.py)는 원천 객체를 복사한 뒤 기존 공식을 적용한다. 최종 반환값과 통합 캐시도 서로 다른 객체를 가진다. `capture_selection=True`인 경우에만 [계산 근거 생성기](../../src/analytics/selection_basis.py)를 사용한다. 이 입력이 없으면 근거를 생성하지 않는다. 관측 중 예외는 원래 선정 반환에 영향을 주지 않도록 격리한다. 첫 관측 이후와 버퍼 종료 뒤에는 스케줄러가 추가 근거 생성을 요청하지 않는다.

후보별로 다음을 보존한다.

| 구간 | 저장하는 값 | 해석의 한계 |
|---|---|---|
| 원천 병합 | source ID, 해당 입력 순위, 병합 당시 점수, 가중치, 가중 점수 | 원천 생성 시점의 원 응답이나 거래소 시각을 뜻하지 않음 |
| 후속 보정 | 원천 가중합 이후 보정의 합계 | 재무·모멘텀·수급 등 각 보정의 미평가/실패와0점은 아직 분리하지 못함 |
| 출현 보너스 | 병합 출현 횟수와 실제 보너스 | 독립 정보원 수가 아님. 같은 계열/파생 신호도 출현 횟수에 포함됨 |
| 정규화 | 적용 전 점수, 반환 후보 집합의 min/max, clamp 또는30~100 변환, 최종 점수·반환 순위 | 정규화된 점수를 독립 원천 기여의 단순 합으로 분배하지 않음 |
| 캐시 | 근거 생성 ID/시각과 통합 캐시 폴백 여부 | 이전 근거가 없는 캐시에는 근거를 새로 만들어 붙이지 않음 |

`source_status_known=false`, `source_as_of_known=false`를 유지한다. 개별 원천 함수가 오류와 정상 빈 결과를 모두 빈 목록으로 반환하는 경우, 통합 함수만으로 이를 복원할 수 없다. 원천 하나가 목록에 없다고 해서 정상0점 기여였다고 판단하지 않는다. 캐시 수정은 이전 버전에서 오염되던 점수를 바꾸므로, 후속 관측은 새 코드/설정의 평가 세대를 선언하고5468208 표본과 같은 버전으로 합치지 않는다.

### 새 수집 규약의 명시 활성화

기존 `runner-first-scan-v1`에는 추가 필드를 허용하지 않고 기존 동작을 유지한다. 후속 연구의 study가 새 `runner-first-scan-v2`를 선언할 때만 capture 안에 다음을 요구한다.

```json
"selection_basis": {
  "version": "selection-basis-v1",
  "max_candidates": 100,
  "max_source_terms": 16
}
```

후보 한도는1~100, 후보별 병합 항은1~16 범위다. 호가 구독의 `channels.max_candidates`와 별개이며 상위3개 호가 관측이 선정 후보 분모를 줄이지 않는다. 버퍼·큐에는 최소 `1+max_candidates`개의 즉시 발생량을 확보한다. 레코드 한도는 최소32KiB, 전체 저장 한도는 최소 `(1+max_candidates)×(max_record_bytes+2048)+2048` 바이트다. 이는 스캔/선정 근거의 최소 저장 예산이고, 호가·주문·구독 기록을 포함한 전체 유량과 성능 검증은 기존 `capacity_evidence_ref` 및 후속 수집 설계에서 별도로 확보해야 한다.

스캔에는 근거 기록이 예정됐는지와 한도를 표시한다. 원래 전체 후보를 먼저 저장한 뒤 후보별 `selection_basis` 레코드를 같은 candidate ID로 연결한다. 근거가 없으면 `unavailable` 행을 남긴다. 저장 유실·한도 초과·형식 오류는 근거 없음과 구분해 incomplete/dropped로 보존하며, 후보를 조용히 잘라 저장하지 않는다. 새 레코드는 갱신된 원장 reader로 읽어야 한다.

### 수집 후 사용

기존 [평가 준비 CLI](../../scripts/prepare_entry_evaluation.py)에 원본 study와 원장을 주면 가격 비교 결과와 함께 `selection_basis` 보고서가 나온다. 후보/기록 예정/저장/계산 근거 보유/캐시/근거 없음/유실/비활성 수를 각각 표시한다. 기록 연결·형식·산술을 확인하며 실제 source 사실이나 수익성을 인증하지 않는다. 일부 후보의 근거가 없어도 남은 근거들의 계산 ID/정규화 조건 일치를 검사한다. 생성시각은 후보 확정시각 이전이어야 하며, 선언 상한 초과를 complete로 주장하는 모순은 거부한다.

가격 계산기는 선택 근거의 ID/시각 연결만 확인한다. 선정 점수를 진입 승인·주문 수량·현금 수익으로 쓰지 않는다. 과거 원장에는 근거가 없다는 사실을 유지하고, 기존 후보 분모와 비용 후 가격 계산은 보존한다.

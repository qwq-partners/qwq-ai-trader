# KIS 미확정 문항의 판단 결정 — 그리고 그것이 드러낸 attach 의 실제 격차 (2026-09-22)

> **한 줄:** KIS 는 질문지에 답하지 않는다. 사용자 지시로 31문항을 **우리가 판단해 확정**했다(전부 "어느 답이 참이어도 안전한 쪽"). 그 결과 설치 차단 사유 1·2·12 는 "증거 대기"에서 "설계로 대체/분해"로 바뀌었다. **그러나 같은 작업의 적대적 심사가, KIS 답과 무관한 새 설치 차단 사유 3건과 attach 가 현행(legacy)보다 약한 지점 10곳을 찾았다.** 임계 경로는 이제 KIS 증거가 아니라 이 격차다.

## 0. 지시와 해석

- **사용자 지시(2026-09-22, 원문):** "나머지 답들도 답변이 없으니 우리가 임의로 판단해서 진행하면 돼. 니가 검토해서 제일 우리에게 이득이 되는 방향으로."
- **coordinator 의 해석:** "이득" = 유리한 답을 가정하는 것이 아니라 **어느 쪽 답이 참이어도 안전한 설계**를 고르는 것. 문항마다 "틀렸을 때 가장 싼 가정"을 채택한다.
- **이 지시가 주지 않는 권한:** `trading_ready` 강제 True·합성 startup 허가, main 병합·배포·재시작·실주문·설정 변경(각각 별도 사용자 확인), MODIFY 지원.
- **과정:** 조사 2(브로커가 강제하는 불변식과 현행 main / engine owner 의 변경 지점, 요청 opus/high) → 설계(요청 opus/high) → 적대적 심사 2관점(돈을 잃는 시퀀스 / 코드 실현 가능성, 요청 opus/xhigh, 설계자와 다른 실행). 읽기 전용·pytest 0·제품 수정 0. 심사 판정: **① BLOCK(must-fix 8) · ② REVISE(must-fix 6)** → 아래는 그 처분을 반영한 결과다. 아래 "coordinator 확인"이라고 적은 것만 coordinator 가 코드로 재확인했고, 나머지 인용은 조사·심사의 보고다.

## 2. 문항별 판단 (Q1~Q31)

원문은 `docs/integrations/kis-execution-evidence-narrowing-2026-09-21.md` ③절. "틀리면"은 채택한 가정이 틀렸을 때의 비용이다 — 전부 **잠기는 쪽(운영 비용·수동 복구 가능)이 조용히 틀리는 쪽(돈 경로)보다 싸다**는 같은 비대칭으로 결정했다.

| 문항 | 채택한 가정 | 틀리면 | 사후 검증 지점 |
|---|---|---|---|
| Q1~Q5 자식행·누적 범위 | 자식행은 독립 행으로 오고 **어느 행이 어느 범위를 누적하는지는 알 수 없다.** 체인이 한 줄이라도 보이면 그 주문의 수량 해석을 포기한다(`evidence.py` 의 chain 차단 유지). 체인은 우리가 만들지 않아도 **사용자의 HTS 수동 취소·정정이 만든다** — 그 경우는 수동 처분 대상 | 차단이 과했다면 전량체결 주문도 최종성을 못 받아 그 종목이 잠긴다. 반대로 풀었는데 누적이 중복이면 체결수량·예약·포지션이 동시에 틀린다 | 운영 일별체결조회 응답의 비식별 기록(§3 D10) |
| Q6·Q24·Q25 취소확인수량·철자·`cncl_yn` | 철자는 둘 다 받고 값이 다르면 malformed · 빈 `cncl_yn` 은 정상으로 인정하지 않는다 · 취소확인수량의 **의미**는 미확정으로 두고 어떤 판정에도 쓰지 않는다 | 빈 값이 정상이면 모든 행이 `malformed_row` — 잠김이고 관측 즉시 드러난다. 반대면 취소된 주문을 정상으로 읽는다 | 같은 기록 — 정상 체결행의 `cncl_yn` 실제 값과 실제 키 이름 두 가지면 닫힌다 |
| **Q7~Q12 취소 최종성** | **취소 최종성은 알 수 없다고 확정한다.** `rt_cd=0` 도, 통보의 "확인"도, 취소가능조회의 부재도 확정 근거로 쓰지 않는다 | 실제로 ACK 즉시 확정이었다면 보호가 느린 것뿐. 확정으로 가정했는데 아니면 취소 위에 얹은 분할 SELL 이 이중 매도가 된다(합계가 보유 안이라 KIS 가 거절하지 않는다) | 없음 — 현재 운영에는 취소 흐름이 자연 발생하지 않는다 |
| Q13~Q15 정정·다단 체인 | **MODIFY 는 영구 미지원.** 답이 와도 채택하지 않는다 | 기능 하나를 안 쓰는 것뿐 | — |
| Q16~Q18 연속조회 일관성 | 페이지 사이에 **중복도 누락도 생길 수 있다** | 일관적이었다면 조회 한 번 더의 비용. 반대면 누락된 미체결 행을 "없음"으로 읽는다(fail-open) | 기록에 응답 `tr_cont` 와 페이지 수 |
| **Q19~Q21 공통 cutoff·지연 상한** | **공통 cutoff 도, 기준시각 필드도, 지연 상한도 없다.** 2026-09-17 계획의 "정지 snapshot cutoff 의 명시적 전체 조회 증명" 요구는 **공개 계약으로 달성 불가**로 판정한다 | 있었다면 더 강한 인계를 못 쓴 것뿐. 없는데 있다고 가정하면 살아 있는 주문 위에 attach 를 설치한다 | 없음(필드가 없다는 것이 관측 내용) |
| Q22~Q23 재시작 절차·통보 재전송 | 권장 절차 문서는 없고 **끊긴 구간의 통보는 재전송되지 않는다** | 재전송이 된다면 가속기 하나를 버린 것뿐 | — |
| Q26 `output2` 라벨 | `output2` 를 어떤 판정에도 쓰지 않는다 | 양쪽 다 비용 0 | 부수적으로 기록 |
| Q27~Q29 거래소 범위 | **"조회 범위를 좁히면 안전해진다"를 부정한다**(좁히면 자식행이 안 보여 최종성 인정이 쉬워진다). 증거 판정의 기준 범위는 운영과 같은 넓은 쪽(`"ALL"`) | 구TR 이 `ALL` 을 무시한다면 넓다고 믿는 범위가 실제로는 KRX 뿐 | 응답 행의 `excg_id_dvsn_cd` 값 분포 — KRX 이외가 한 번이라도 보이면 Q27 이 닫힌다 |
| Q30 구TR 종료 | 사전고지 없이 막힐 수 있다 — 대비는 main 의 `KIS_TR_SET`(PR #80, 기본 legacy) | 비용 낮음 | 구TR 조회가 거절되는 날(조회부터 드러난다) |
| Q31 유량 | 공용 리미터 10/s 유지, 공식 수치(18)로 올리지 않는다 | 한도가 더 높았다면 조회가 느린 것뿐 | EGW00201 발생률 |

## 3. 설계 결정 (심사 처분 반영)

| # | 결정 | 상태 |
|---|---|---|
| **D1** | SELL 안전의 뼈대 = **브로커의 초과매도 거절 + owner 의 `held − reserved` 클램프.** 매도가능수량(`ord_psbl_qty`·`TTTC8408R`)을 읽는 코드는 만들지 않는다 — 보유수량의 두 번째 정본이 생기고 어느 쪽이 이기는지의 규칙이 owner 에 없다. **심사 처분:** ① "거절 = 안전망"이 아니라 **"거절 = 보호 실패"** 다 — owner 는 사용자의 수동 매도를 배울 경로가 없어 같은 수량 요청이 영원히 거절만 반복될 수 있다 → 거절 사유에 `APBK0400`·"주문 가능한 수량"이 오면 즉시 수동 개입 알람 ② 불변식은 "코드가 강제한다"가 아니다 — N2 참고 ③ **"살아 있는 미체결 SELL 이 주문가능수량을 묶는다"는 저장소 어디에도 없는 가정**인데 main 은 이미 돈 경로에서 사실로 쓴다(`origin/main:src/core/engine.py:2322-2326`). 같은 문장을 engine 은 미확인으로, main 은 전제로 쓴다는 것을 기록한다 | 확정 |
| **D2** | attach 는 취소를 보내지 않는다(S4 결정 ② **잠정 유지**) · 분할 SELL 은 종목당 살아 있는 SELL 1건 · 보존식 기반 재발행은 지금 설계하지 않는다(파서의 보존식은 등식이 아니라 부등식이라 "보존식이 보인다"를 표현할 수 없다). **coordinator 의 방향 결정:** 이것을 영구 결정으로 두면 attach 는 영원히 설치할 수 없다. **목표는 어젯밤 main 이 도달한 수준과의 동등**이다 — 취소 뒤를 소멸/생존/판단 불가(시간 상한 180초)로 가르고, 전량 청산은 브로커 거절을 뒤에 두고 즉시 폴백·분할은 생존이 확인되면 유지(`origin/main:src/core/engine.py:2384-2505`). 그 설계는 §5 의 전제 단계(P0) **뒤**에 한다 | 잠정 |
| **D3** | BUY 예약은 만료로 풀지 않는다(`FINAL_EXPIRED` 미지원 유지). **심사 처분:** "그 종목은 일자 전환까지 잠긴다"는 서술은 **틀렸다** — 비terminal submit 은 `_quiescence_reason` 을 통해 일자 전환 자체를 BLOCKED 로 만들고, `reset_daily` 는 attempts 를 지우지 않으며, BLOCKED 로 끝난 전환 시도가 admission 을 닫아 그 프로세스의 보호 SELL 까지 멈춘다. 해제는 운영자 처분까지다 | 확정(서술 정정) |
| **D4** | UNKNOWN 의 전역 정지를 좁힌다 — **좁히는 것은 `blocked_unknown` 하나뿐**이고 `observed != applied`·`evidence_conflict` 는 전역으로 남긴다(같은 `_require` 의 세 조건 — 뒤의 둘은 그 종목에 국한된다는 근거가 없다). 미해결 BUY 가 같은 종목의 보호 SELL 을 막지 않게 한다. **순서:** 종결 증거의 생산자가 0건인 동안(N3) 게이트를 여는 변경은 하지 않는다 → P0 뒤 | 확정·P0 뒤 |
| **D5** | UNKNOWN 의 해제는 증거 매칭으로 하지 않는다(`order_ref is None` 에서 신원 검사를 완화하지 않는다). 프로세스를 세우고 사람이 state 를 처분하는 **운영 절차**(runbook, 코드 0줄) | 확정 |
| **D6** | `trading_ready` 는 계속 False. 여는 술어는 증명이 아니라 **차가운 시작**으로 정의한다(장중 재시작 설치 금지). **심사 처분:** ① 술어는 "오늘 attempt 0건"이 아니라 **"비terminal attempt 0건 AND 남은 예약 0"**(attempt 행에 날짜 필드가 없어 소박한 형태는 첫 거래일 뒤 영구 거부가 된다) ② 설치 게이트의 취소가능조회는 **운영이 매일 쓰는 파라미터와 바이트 단위로 같게** — 수집기는 `INQR_DVSN_1="1"`, 운영은 `"0"` 이고 저장소는 이 값의 의미가 두 갈래라고 스스로 적는다(0행 = 정지점이라는 판정이 fail-open 이 될 수 있다) ③ 이것은 "거부 3종 추가"가 아니라 설치기에 I/O·계좌 식별자·원장 TR 1건을 새로 들이는 변경이다 | 확정·P0 뒤 |
| **D7** | 보호 SELL 전용 모드는 **지금 만들지 않는다.** D6 이 장중 재시작 설치를 금지하므로 그 모드로 가는 전이가 없고(도달 불가 코드), 게이트 리터럴 단일화조차 시험 7파일의 `trading_ready` monkeypatch seam 과 부딪힌다. 장중 재시작 정책을 정할 때 다시 연다 | 폐기(보류) |
| **D8** | 가격 없는 SELL 은 계속 거부(차단 사유 10 그대로) | 유지 |
| **D9** | KR 체결통보는 붙이지 않는다 — REST 조회가 정본이고 통보는 없는 것으로 설계한다 | 확정 |
| **D10** | 증거 기록기는 engine 수집기가 아니라 **운영(main)의 일별체결조회 응답 수신 지점**에 붙인다. 목표는 취소 최종성이 아니라 필드 철자·`cncl_yn` 값 집합·`excg_id_dvsn_cd` 분포·페이지 수. 레코드에 실제 `tr_id` 를 남긴다 — **기본 `legacy` 에서는 구TR 판의 Q24·Q25·Q27 만 닫힌다**(신TR 판은 `KIS_TR_SET=new` 전환이 선행). live 파일·배포가 필요하므로 **사용자 확인 전에는 착수하지 않는다** | 사용자 확인 대기 |

## 1. 목적과 완료 조건

`docs/operations/claude-handoff-b1-runner-2026-09-28.md` §8 의 표 전부가 아니라, 두 가지를 만족하는 데 필요한 만큼만 다룬다.

1. **계측 무결성:** 계좌의 모든 KR 체결이 writer 하나를 거쳐 DB `trades`/`trade_events` 에 한 번 기록된다. 기록하지 못한
   체결은 보정 이벤트로 **보이게** 남는다. 이것이 설계 A(main `docs/superpowers/specs/2026-09-28-kodex200-excess-return-ledger-design.md`)의 원천이다.
2. **KIS 한 경로로 안전한 실거래:** 봇의 KR 주문 POST 는 모두 한 함수(킬스위치·감사·무재전송)를 지난다. 포지션·현금·
   미체결을 쓰는 주체도 하나다. 현행 위험 한도(`config/*.yml`)는 그대로 두고 한도 검사도 약해지지 않는다.

Toss 는 조회·관측 보강만 맡는다. 주문·잔고·계좌는 KIS 만 쓴다(사용자 09-28 재확인). US 는 영구 중단이라 제외한다.

## 3. 원칙

1. **브로커가 강제하는 불변식을 뼈대로 쓴다**(09-22 사용자 지시).
   - I1 **매도가능수량을 넘는 매도는 KIS 가 거절한다.** 거절은 안전망이 아니라 "보호 실패" 신호다(D1).
   - I2 **봇이 내는 KRX 정규·마감 DAY 주문은 그 세션일 안에 끝난다.** 봇은 NXT·SOR·시간외·예약주문을 내지 않으므로(D11) 그날
     20:00 이후에는 봇 주문이 살아 있지 않다. **사용자·외부 주문에는 I2 를 적용하지 않는다.**
   - I3 **밤(20:05~다음 날 08:00 전)에는 살아 있는 봇 주문이 없고 새 봇 체결이 생기지 않는다.** 그 시각의 잔고는 **경제 checkpoint**
     (수량·평단·현금)로 쓸 수 있다. 다만 조회 응답의 기준시각·지연 상한이 없으므로(Q19~21) 체결 **기록**의 완전성은 증명하지 않는다 —
     기록 완전성은 거래일별로 따로 표시한다(D12).
   - 현금을 넘는 매수의 거절은 불변식으로 쓰지 않는다. 미수 허용 계좌라면 거절되지 않기 때문이다.
2. **잠기는 쪽이 조용히 틀리는 쪽보다 싸다**(판단 결정 문서 §2). 잠금 범위는 원인의 범위와 같게 둔다: 종목 원인은 그 종목
   (방향별), 현금 원인은 BUY 전체, 저장 무결성 원인은 전체.
3. **장벽을 더하지 않고 규칙을 빼서 단순하게 만든다**(09-28 사용자 지시). 봇이 취소·정정을 내지 않으면 봇이 만든 취소 체인은 없다.
   사용자 HTS 취소·정정이 만든 체인은 Q1~5 처분(그 주문의 수량 해석 포기 → 수동 처분)을 따른다.
4. **한도는 약하게 하지 않고 봉인만 뺀다.** owner 는 main 이 오늘 dispatch 직전에 하는 한도 판정을 in-flight 포함으로 다시 한다.
   빼는 것은 결정 사실의 generation/seal 재검증뿐이다.
5. **v1 의 안전 기준은 "legacy(main) 이상"이다.** v1 이 legacy 보다 나빠지는 시퀀스는 막는다. legacy 에도 있는 한계는 같은 수준으로
   남기고 §12-2 에 적는다 — 그것을 없애려고 새 방어 체계를 만들지 않는다.

## 6. 시작·야간·점검 절차

### 6-0. 모든 시작의 공통 앞단

1. `AccountLease` 를 잡는다(실패하면 기동하지 않는다 — 두 번째 프로세스·CLI).
2. 저장소가 있으면 `restore()` 뒤 **저장된 거래일과 오늘 거래일을 먼저 비교**한다. 저장된 날이 과거면, 오늘 체결을 적용하기 전에
   과거 날짜들의 봇 attempt 를 `order_closed`(I2) 로 표시하고, 지금이 밤 창(20:05~08:00 전)이면 D12 ② 야간 대사를, 장중이면 D12 ⑤ 처럼
   `accounting_pending` 으로 닫아 예약을 푼다. 그 뒤 일자 전환(`day_recovery`)을 하고 나서야 오늘 체결을 적용한다
   (`economics.py:364` 의 날짜 일치 조건을 교차일 예외 없이 지킨다). 과거 날짜의 `execution_day_status` 는 `incomplete` 로 두고 D12 ③ 백필을 기다린다.

### 6-1. 차가운 시작 (20:05 이후 ~ 08:00 이전)

1. §6-0.
2. **최초 설치**(owner 저장소가 빔, legacy → attach): ① legacy `sync_from_kis` 를 한 번 실행한다(최선 노력 — 반환이 DB 기록 완료를 뜻하지
   않는다: 예외를 삼키고, 종목 단위로 건너뛰며 `buy_fills[0]` 만 쓰고, DB 쓰기는 비동기 큐다 — `trade_storage.py:890·987-989·215`)
   ② 거래소 미체결(TTTC8036R, 전 페이지, 운영과 같은 파라미터)이 0건이어야 한다 ③ 잔고(TTTC8434R)·매수가능(TTTC8908R — **실패하면
   예수금 폴백을 쓰지 않고 설치를 거부**)으로 checkpoint(보유·평단·현금)를 만든다 ④ 보유 종목마다 **이 시점에 DB 에서 읽은** 열린 trade
   (같은 종목, 청산 전, 가장 최근 진입)를 연결하고, 없거나 둘 이상이면 `KIS_SYNC_` 새 trade 를 연다 ⑤ 오늘 체결 전부를 **경제 커서**로 둔다
   ⑥ **설치일의 `execution_day_status` 는 `incomplete` 로 쓴다** — legacy 행에는 증분 키가 없어 백필로 중복을 막을 수 없으므로 설치일은
   백필하지 않고 설계 A 에서 그날을 건드린 포지션을 뺀다 ⑦ 면제 목록을 옮긴다.
3. **재기동**(저장소 있음): §6-0 으로 과거 날짜를 처리한다.
4. 거래소 미체결이 0건이 아니면(사용자·외부 주문, I2 비적용) 설치를 거부한다. 저장소가 clean 이 아니면 D14 에 따라 legacy 로 가지 않고
   주문 정지·경보한다.
5. `trading_ready = True`.

### 6-2. 따뜻한 시작 (장중 재시작)

§6-0(과거 날짜가 있으면 `accounting_pending` 처리 후 일자 전환) → 오늘 체결 적용(D17, 커서 이어받기) → 거래소 미체결 중 **기존 attempt 의
`OrderRef.key` 와 맞지 않는 행만** 미상 주문으로 입양(방향별 D13 잠금, 방향별 예약 = 잔량; 주문번호·잔량이 확인된 사용자 SELL 은 식별된
외부 SELL) → 잔고·현금은 D15 규칙대로(조용한 종목만 채택) → `trading_ready`. 오늘 attempt 는 닫지 않는다. 입양한 봇 주문은 그날 장 종료·
야간 대사가 닫는다. 사용자 주문은 I2 를 적용하지 않으므로 다음 차가운 시작 4번이 처리한다.

### 6-3. 점검과 호출 예산

- 신선도: 동기화 조회의 **요청 시작 시각**이 owner 의 그 종목(또는 현금) 최종 변경보다 뒤일 때만 점검·채택에 쓴다. 채택은 D15 ⓐ·ⓒ 의
  조용한 종목·계좌에 한정하므로 우리 주문의 체결과 경합하지 않는다.
- 체결 수집 주기: 봇의 미해결 attempt 가 있으면 5초, 없으면 60초(외부 체결 포착용). 원장 TR 은 기존 리미터(`LEDGER_TR_IDS`, 1.05초·8434R
  2.1초 간격)를 거친다. 시작·장 종료·야간 대사의 원장 TR 은 4종(8434R·8908R·0081R·8036R, +페이지, 백필은 0081R 날짜 지정)이고, 장중에는
  거절 절차(D15)의 종목 지정 8036R 1회가 더해진다.
- EGW00215 는 09-28 결정대로 조치하지 않는다. 60초 기본 수집 주기는 legacy(미해결 주문이 있을 때만 2~5초)보다 장중 원장 호출을 조금 늘린다 —
  canary 에서 거절 건수를 본다.

## 8. 계측 연결 (D17)

- 계좌 전체 체결 → owner 적용(봇/외부) → 한 트랜잭션(`execution_journal` + `trades`/`trade_events` + 완료 표식). 증분 키 =
  (`OrderRef.key`, 누적 체결 수량, 누적 체결 대금) — 경제 적용과 projection 이 같은 키를 쓴다. 트랜잭션 도중 종료되면 전부 없고, 재배달은
  표식으로 한 번만 된다.
- trade 연결: owner lot 이 새로 열릴 때(0 → 양수, 또는 D17 의 "닫힌 lot 뒤 같은 BUY 증분") 새 `trades` 행, 부분 체결은 `trade_events` 로 붙인다.
  §6-1 checkpoint 는 기존 열린 trade 에 연결한다. 봇 체결은 전략·`entry_risk`(`market_context`)·`exit_type`·체결가·수량·시각을 legacy
  `run_fill_check`(`kr_scheduler.py:2860~`)와 같은 필드로 쓴다. 외부 체결은 거래 id `KIS_SYNC_` 접두와 `entry_reason="external_fill"` 로
  쓴다 — 봇 보유 종목에 외부 BUY 가 더해지면 별도 `KIS_SYNC_` trade 가 되어 설계 A 에서 `lots_ambiguous`·`sync_entry` 로 빠진다.
  D12 야간 보정·D15 조용한 종목 채택은 `kis_sync` 유형 이벤트다(설계 A 에서 동기화 표시). `execution_day_status` 가 `incomplete` 인 날을
  건드린 포지션은 설계 A 에서 `record_incomplete` 로 빠진다(설계 A 구현 때 사유 추가 — 설계 A 문서에 후속으로 반영).
- 인수 조건: 합성 체결에서 설계 A 의 회계 대조(Σ행 `net_pnl` = Σ`trades.pnl`)가 성립하고, 같은 증분을 두 번 배달해도 행이 한 번만 생기며,
  HTS 왕복(같은 날 매수·매도)이 외부 체결 2건으로 남는다.
- legacy 모드에서는 지금 경로를 그대로 쓴다. 모드가 바뀌어도 설계 A 의 입력 계약은 같다. 설계 A §10 의 "놓친 체결" 한계는 attach 에서
  D17 수집으로 대체되고, 그래도 놓친 것은 야간 보정으로 보이게 남는다.

## 12. legacy 대비 차이

### 12-1. 달라지는 동작 (숨기지 않는다)

1. 정규장 SELL 이 매수1호가 지정가에서 **시장가**로 바뀐다. 호가가 얇으면 한 호가보다 아래에서 체결될 수 있다. 대신 90초 미체결 →
   취소 → 시장가 폴백 경로가 없어진다. 시장가 잔량(가격제한 잠김)은 다음 정규장에서 다시 판정한다.
2. 수동 매수 지정가가 체결되지 않으면 **취소하지 않고** 당일 소멸까지 둔다. 그동안 그 종목 BUY 는 잠기고 현금은 예약된다(그 종목의 보호 SELL 은 된다).
3. 장전·NXT·시간외 주문이 없다.
4. 따뜻한 시작에서 입양한 미상 주문의 종목은 당일 끝까지(사용자 주문이면 다음 차가운 시작까지) 방향별로 잠길 수 있다.
5. UNKNOWN BUY 가 나면 **그날 남은 시간 모든 BUY** 가 보류된다(다음 야간 대사가 푼다).
6. 시작 실패 + clean 아님이면 legacy 로 가지 않고 주문을 멈춘다(운영자 처분). 야간 대사가 08:00 까지 안 끝나면 그날은 BUY 없이 열고,
   수량·보호는 D15 의 조용한 종목 채택으로 회복한다(활동이 있던 종목은 다음 야간 대사까지 owner 수량).
7. 축출 쿨다운이 재시작을 넘어 유지된다(더 엄격해진다).
8. W P1 결정을 그대로 받는다: 보유기간 판정이 달력일에서 **영업일**(ExitManager 정본)로 바뀌고, 결정이 없는 틱은 20초마다 기록해
   **순간 고점을 놓칠 수 있다**(트레일링 기준 고점이 legacy 보다 낮게 잡힐 수 있음).
9. 진입의 레짐·패널 결정 사실을 dispatch 직전에 다시 봉인하지 않는다. **지금 운영과 같고**, W 와 비교할 때만 약해진다.

### 12-2. legacy 와 같은 수준으로 남기는 한계 (원칙 5)

비교는 오류 가능성뿐 아니라 **복구 조건과 지속 시간**까지 같을 때만 "같은 수준"으로 적는다.

- 같은 종목의 서로 다른 주문 사이 체결 순서는 누적 조회로 복원하지 못한다 — 조회 순서대로 적용한다(legacy `check_fills` 도 같다).
  평단 계산이 실제 순서와 다를 수 있다. 복구: 야간 대사가 잔고 평단으로 맞춘다(legacy 는 30초 동기화) — 수량은 같고 평단만 하루까지 다를 수 있다.
- 최초 설치일 이전의 legacy DB 누락(17시 이후 체결 등)은 복구하지 않는다. 설치일은 `incomplete` 로 표시돼 설계 A 에서 빠진다 — legacy 는 누락을
  표시조차 하지 않는다.
- 사용자가 봇과 같은 종목을 HTS 로 매매하면 그 종목 거래는 설계 A 에서 빠진다(lot 구분 불가 — legacy DB 도 구분하지 못한다).
- **legacy 보다 느린 복구(숨기지 않는다):** 오늘 활동이 있던 종목의 누락 체결은 장중에 잔고로 채택하지 않고 야간 대사까지 owner 수량으로 남는다
  (legacy 는 30초 동기화로 즉시 맞춘다). 과다 수량의 SELL 은 I1 거절 → D15 절차, 과소 수량은 그 차이만큼 당일 보호가 늦는다. 채택하지 않는 이유는
  우리 주문 체결과 지연된 잔고의 경합(1회차 P1-6)이다 — §14 에서 사용자에게 이 교환을 묻는다.

## 14. 사용자 확인이 필요한 결정

리뷰 승인과 별개로, 아래는 이전 결정이나 운영 동작을 바꾸므로 구현(B1) 착수 전에 사용자가 정한다.

1. **D12** — D3("만료로 예약을 풀지 않음")을 개정해, 주문이 끝나고(I2) 밤 잔고 checkpoint 로 닫힌 봇 DAY 주문에서만 예약을 푼다. 08:00 까지 대사가 안 되면 `accounting_pending` 으로 풀고 그날 BUY 를 보류한다(공개된 예외). 놓친 체결은 잔고 보정 + DB 백필로 남긴다(교차일 경제 재생 없음).
2. **D16** — W 의 결정 사실 재봉인(B2/B3 qualification·seal)을 v1 설치 경로에서 뺀다. 한도 검사는 그대로 둔다(B2-0 인벤토리).
3. **§11** — N4097·native·cold 소유권·전체 C/F/G/R 을 설치 조건에서 빼고 §13 의 정상·장애 인수 시나리오로 바꾼다.
4. **D14** — 시작 실패 + clean 아님이면 legacy 로 가지 않고 주문을 멈춘다. legacy 폴백은 clean(통일 술어)일 때만(= 현행 재시작 수준).
5. **§12-1-1** — 정규장 SELL 을 매수1호가 지정가에서 시장가로 바꾼다.
6. **§12-1-8** — W P1 의 보유기간 영업일 기준과 20초 고점 표본을 받아들인다(청산 시점·트레일링 고점이 달라진다).
7. **원칙 5** — v1 의 안전 기준을 "legacy 이상"으로 두고, §12-2 의 legacy 공통 한계는 새 방어 없이 남긴다.
8. **§12-2 마지막 항** — 오늘 활동이 있던 종목의 누락 체결은 장중 잔고로 맞추지 않고 야간 대사까지 둔다(legacy 는 30초). 경합 없는 조용한 종목만 장중에 채택한다.

## ① 이 문서가 무엇이고 무엇이 아닌가

**이 문서는 세 가지다.**

1. 2026-09-21 공개 1차 출처(KIS API 포털의 가이드·응답예제·공지·FAQ, `koreainvestment/open-trading-api` 고정 revision `b4e6249`)를 다시 읽어, [증거 요청 목록](kis-execution-evidence-request-2026-09-18.md)의 **6개 계약 행 각각에서 "이번에 더 고정된 것"과 "여전히 입증되지 않는 것"을 분리한 기록**이다.
2. 남은 공백을 메우기 위해 **KIS 에 그대로 보낼 수 있는 질문지**(③)다.
3. 사용자가 이미 보유한 자료에서 **비식별 응답을 모을 때의 순서와 경계**(④)다.

**이 문서는 다음이 아니다.**

- **자료 확보가 아니다.** 6개 계약 행 중 이번 조사로 닫힌 행은 **0개**다. 닫힌 것은 세 가지 부분 사실뿐이다: (a) 전량체결 종결의 공식 판정 방법, (b) "체결통보 수신 ≠ 당사 원장 반영 완료"라는 공식 경고, (c) 통보에 최종성 필드가 없다는 공식 확인.
- **거래 허용이 아니다.** `trading_ready` 는 계속 `False`(`src/execution/safety/runtime.py:62-65`, `:814`), 모든 MODIFY 는 미지원, attach 설치 차단 사유는 그대로다.
- **실 API 호출·실주문이 아니다.** 거래 API 호스트(`openapi`/`openapivts`/`ops.koreainvestment.com`)에 어떤 요청도 보내지 않았고 자격증명·계좌정보를 쓰지 않았다. 읽은 것은 공개 포털의 문서 엔드포인트와 GitHub raw 파일뿐이다. ④의 수집도 **시험용 실주문을 요구하지 않는다** — 이미 존재하는 승인 자료의 인수 시나리오다.
- **필드 정의를 경제적 보장으로 승격하지 않는다.** 필드 이름과 값 목록이 있다는 사실은 "그 값이 어느 주문 범위의 무엇을 뜻하는가"를 말하지 않는다. 아래에서 `공식 근거` 로 실은 것은 인용문이 직접 말한 범위까지이고, 그 밖은 전부 `확인 못함` 으로 분리했다.

**여전히 입증되지 않는 것**

- 7개 필드 각각이 **어느 주문 범위의 누적인가** — 1차 출처에 문장이 없다.
- `TTTC0084R`(취소가능조회)의 행 단위 설명이 `TTTC0081R`/`TTTC8001R` 의 동명 필드에 적용된다는 공식 문장은 **없다**.
- 원행과 자식행을 **합산했을 때 중복되는가**. 위 AMEND 예제는 "취소가능조회의 표시 규칙"을 보여 줄 뿐이고, 원주문 권리의 소멸이나 수량 보존식을 말하는 문장이 아니다. 예제는 미체결 1주·2행이라 부분체결·다단정정·부분취소를 전혀 담지 않는다.
- 일별주문체결조회 `output1` 의 **행 구성 규칙**(자식행이 목록에 오르는가, 원행이 함께 오는가) — 공식 예제에 정정/취소 자식행도 `cncl_yn='Y'` 행도 부분체결 행도 **하나도 없다**(예제 2행은 둘 다 `BUY REJECT`).
- 어긋난 라벨 중 **어느 쪽이 실제 응답 의미인가**.

**그래서 필요한 것**

`TTTC8001R`/`TTTC0081R` `output1` 에서 ① 정정/취소 자식행의 등재 여부 ② 등재될 때 원행의 존속 여부 ③ 7개 수량 필드 각각의 주장 범위(그 행의 주문인가, 원주문 체인 누적인가)를 **문장으로** 받는 것. 질문지 Q1~Q6, Q24~Q26.

### 행 3. 다단 정정

> 수량 증감·가격 변경·부분체결 중 정정에서 원/자식별 목표량·체결량·잔량 관계와 주문번호 연결 규칙은?

**이번에 더 고정된 공식 근거**

- 상한 하나: "정정이 가능한 수량은 원주문수량을 초과 할 수 없습니다"(위 order-rvsecncl apiSummary).
- 연결 규칙의 방향 하나: `orgn_odno | 원주문번호 | 정정/취소주문 인경우 원주문번호`(TTTC0084R 가이드). 즉 자식행이 원주문번호를 들고 다닌다.
- 취소·정정은 **새 `ODNO` 를 채번한다**(order-rvsecncl resAuth 의 `ODNO`).

**여전히 입증되지 않는 것**

- 다단 정정에서 **원/자식별 목표량·체결량·잔량의 관계식**. 공식 문장은 상한 한 줄뿐이다.
- "이미 체결된 건"이 **부분체결을 포함하는지** 불명확하다.
- `psbl_qty` 를 확인한 뒤 실제 취소가 도달할 때까지의 **경합 처리**.
- 2단 이상 정정에서 `orgn_odno` 가 **최초 원주문을 가리키는지 직전 부모를 가리키는지**.

**그래서 필요한 것**

이 행은 **제품이 모든 MODIFY 를 미지원으로 두고 있으므로 지금 당장의 차단 사유는 아니다.** 다만 attach 설치 이후 정정을 열려면 위 관계식을 문장으로 받아야 한다. 질문지 Q13~Q15.

- 페이지 도중 체결이 발생할 때의 **중복·누락·재정렬 보장**.

**여전히 입증되지 않는 것**

- **공유 cutoff/sequence 는 존재하지 않는 방향의 증거만 쌓였다.** 두 조회가 같은 원장 cutoff 를 공유한다는 문장도, 가능수량 조회가 원장 최신임을 보장한다는 문장도 없다.
- **시차의 상한이 없다.** 위 2025-05-20 공지는 오히려 "주문 폭주로 인한 … 비동기 처리"를 상한 없는 사유로 열거한다.
- **3개월 이내 당일 조회(`TTTC0081R`/`TTTC8001R`)의 지연 상한.** 위 경고가 이 TR 에 적용되지 않으므로 "지연 없음"의 근거로도 "지연 있음"의 근거로도 쓸 수 없다.
- **놓친 통보의 재전송·전역 sequence·갭 복구 프로토콜.** 26개 통보 필드에 sequence 계열이 없고, KIS 배포 코드의 재접속 경로도 "재연결 + 전 구독 재등록 + 1초 대기"뿐이며(`examples_llm/kis_auth.py` `KISWebSocket.__runner`, 715-731행) 갭 조회를 하지 않는다. 다만 이는 **"재전송이 없다"는 명시적 부정문이 아니라 부재의 결합**이다.
- `120 TPS` 와 `1계좌당 1초당 18건` 은 **서로 다른 축**이다(원장 유량정책 vs 계좌 유량). 한 축에 놓고 비교할 수 없다. `MEMORY.md` 의 "계좌당 초당 1건"은 두 문장 중 어느 쪽과도 직접 대응하지 않는다 — 별도 확인 항목이다.
- `0` 보유수량 표시 규칙은 **표시 규칙이지 최초 인계 cutoff 가 아니다.** 오히려 "같은 잔고가 두 번 같게 나왔다"를 미체결 부재의 증거로 쓰면 안 되는 이유를 하나 더한다.

**그래서 필요한 것**

이 행이 **attach 설치 차단 사유 2번의 정확한 자리**다(`docs/operations/claude-migration-handoff-2026-09-20.md:21` — "`trading_ready` 를 여는 실제 startup 대사가 없다 … §3 최초 잔고/체결 cutoff 증거 + 10A3"). 필요한 것은 (a) 공유 cutoff 가 있는가/없는가의 명시적 답 (b) 없다면 KIS 가 권하는 재조정 절차 (c) 당일 조회 지연의 정량 상한 또는 "상한 없음"의 명시. 질문지 Q19~Q23.

## ④ 비식별 응답 수집 체크리스트

> **사용자가 직접 수행한다.** 시험용 실주문·실 API 호출을 요구하지 않는다 — **이미 존재하는 승인 자료**에서 아래 묶음을 골라내는 작업이다. 자료가 없는 시나리오는 "없음"으로 기록하고 **비우는 것이 정답**이다(없는 값을 만들지 않는다).

### 공통 규칙 (모든 시나리오에 적용)

**비식별**
- API 키·secret·access/refresh token·인증 header·실계좌번호·고객정보는 **받지 않는다**. 원문 자격과의 mapping 도 저장소에 보관하지 않는다.
- 식별자는 **사례 안에서 일관된 가명**을 쓴다(`ODNO 0001569136 → ORD-A`, 그 자식 `0001569139 → ORD-A1`). 체인 관계를 잃는 무작위 재치환은 인수 증거로 쓰지 않는다.
- `CANO`·`ACNT_PRDT_CD`·`CUST_ID`·`ACNT_NO`·`ACNT_NAME`·`BRNC_NO` 는 고정 더미로 치환한다. `ord_gno_brno`(주문채번지점번호)는 **원/자식 대조에 쓰이므로 값 자체는 가명화하되 같은 사례 안에서 일관되게** 둔다.
- 종목코드(`pdno`)는 가명화해도 되고 실제로 두어도 된다 — **다만 한 사례 안에서 일관**해야 한다.

**보존**
- 각 묶음에 **요청 시작·응답 완료의 timezone-aware 시각**과, 응답에 **실제로 존재하는** 시장/주문/체결 시각(`ord_tmd`, `infm_tmd`, `STCK_CNTG_HOUR`)을 함께 적는다. **없는 시각은 "없음"으로 기록한다.**
- 연속조회는 **페이지 순서대로** 요청 `tr_cont`·요청 `CTX_AREA_FK100`/`NK100`, 응답 `tr_cont`·응답 cursor 를 모두 남긴다. 실패하거나 잘린 페이지도 그대로 남긴다.
- 수량 보존식·금액/수수료 차분·페이지 연결·시간 순서가 **비식별화 과정에서 달라졌는지 기록**한다. 바꾼 숫자를 원본 실계좌 사실로 표현하지 않는다.
- `response: []` 인 예제 파일을 실제 빈 조회로 바꾸지 않는다.

**저장 경계**
- 승인 전 원자료를 **Git 에 넣지 않는다**. 승인 범위와 비밀정보 검사를 확인한 뒤 최소한의 fixture/계약 근거만 별도 리뷰한다.
- 이 worktree 기준 임시 보관은 스크래치패드에만 둔다. 운영 `.env`·`~/.cache/ai_trader/`·`logs/` 는 자료원이 아니다.

### 시나리오별 수집 순서

#### 1. 미체결 원주문 → 취소 접수 → 최종 확정
| 순서 | 무엇을 | TR / 통보 | 남길 것 |
|---|---|---|---|
| 1-1 | 취소 직전 미체결 상태 | `TTTC8036R` 또는 `TTTC0084R` 전체 페이지 | 원주문 행의 `odno`·`ord_qty`·`tot_ccld_qty`·`psbl_qty` |
| 1-2 | 취소 주문 접수 응답 | `TTTC0803U`/`TTTC0013U` | `rt_cd`·`msg_cd`·`msg1`·`ODNO`(자식)·`KRX_FWDG_ORD_ORGNO`·`ORD_TMD` |
| 1-3 | 취소 접수·확인 통보 | `H0STCNI0` 전 프레임 | `CNTG_YN`·`RCTF_CLS`·`ACPT_YN`·`RFUS_YN`·`CNTG_QTY`·`ODER_QTY`·`ODER_NO`·`OODER_NO`·`ORD_EXG_GB`·`STCK_CNTG_HOUR` — **접수 통보와 확인 통보를 각각 별개 프레임으로** |
| 1-4 | 취소 이후 조회 | `TTTC8001R` 또는 `TTTC0081R`, `CCLD_DVSN="00"`(전체) 전체 페이지 | 원행·자식행 **둘 다**. `cncl_yn`·`cncl_cfrm_qty`(또는 `cnc_cfrm_qty`)·`rmn_qty`·`rjct_qty`·`tot_ccld_qty`·`tot_ccld_amt`·`orgn_odno` |
| 1-5 | 취소가능 목록 재조회 | `TTTC8036R`/`TTTC0084R` | 해당 주문번호의 **부재 여부**와 조회 시각 |

#### 2. 부분체결 → 취소와 추가 체결의 경합
1-1~1-5 와 같은 순서에 **다음을 추가**한다.
- 취소 접수 **직전**의 `TTTC8001R` 스냅샷(부분체결 상태)과 **직후** 스냅샷을 각각 남긴다.
- `H0STCNI0` 의 **체결 통보(`CNTG_YN=2`)와 취소 접수/확인 통보를 시간 순서대로 전부** 남긴다. 취소 접수 이후에 도착한 체결 통보가 있으면 **그것이 이 조사의 핵심 증거**다.
- 최종 `ord_qty` / `tot_ccld_qty` / `cncl_cfrm_qty` / `rmn_qty` / `rjct_qty` 다섯 값을 함께 적어 **보존식이 성립하는지** 확인할 수 있게 한다.

#### 3. 부분체결 후 정정 → 다시 정정/부분취소 (다단 체인)
- 각 정정 단계마다 **정정 직전 `TTTC8036R` 의 `psbl_qty`** → **정정 접수 응답의 새 `ODNO`** → **정정 이후 `TTTC8001R` 전체 페이지** 순서로 한 묶음씩.
- 체인의 모든 주문번호를 `ORD-A` / `ORD-A1` / `ORD-A2` 식으로 **세대가 드러나는 가명**으로 잇는다. 각 행의 `orgn_odno` 가 어느 세대를 가리키는지가 Q14 의 답이 된다.
- `QTY_ALL_ORD_YN` 과 `ORD_QTY` 요청값도 함께 남긴다(부분취소 여부 판별에 필요).

#### 4. 전체 조회 중 페이지 전환과 체결 발생
- `TTTC8001R`/`TTTC0081R` 을 `CCLD_DVSN="00"` 으로 **여러 페이지가 나오는 범위**에서 조회한 전 페이지.
- 페이지마다 **요청 `tr_cont`**(첫 페이지 공백, 이후 `N`), **요청 cursor**(`CTX_AREA_FK100`/`NK100`), **응답 `tr_cont`**(F/M/D/E), **응답 cursor**, **요청 시작·응답 완료 시각**.
- **같은 범위를 한 번 더 조회한 두 번째 수집본**을 함께 남긴다 — 두 수집본의 행 집합 차이가 Q16~Q18 의 실증이 된다.

#### 5. 재시작 시 최초 인계 (보유 + 미체결 + 외부/수동 주문 공존)
- 순서 고정: **`TTTC8434R`(잔고, 전 페이지) → `TTTC8036R`(미체결) → `TTTC8001R`(당일 전체) → 다시 `TTTC8434R`**.

### 5-3. 차단 사유 12 (UNKNOWN 한 건이 attach 의 모든 새 명령을 멈춘다)

- 현재: `src/execution/safety/commands.py:346-348` 의 `_require(attempt['observed_quantity'] == attempt['applied_quantity'] and not attempt.get('evidence_conflict') and attempt['state'] != 'blocked_unknown', 'unresolved_execution_evidence')` 가 **종목·side·kind 를 가리지 않고** 새 명령을 거부한다 — 손절 SELL 과 CANCEL 도 포함된다(범위 한정: 전역 정지를 일으키는 것은 SUBMIT 의 UNKNOWN 행이다).
- **해제 수단이 `lifecycle.reconcile` 뿐인데 그 제품 호출자가 0건이다.** `parse_order_evidence`·`lifecycle.reconcile`·`KISBroker.get_execution_daily/cancelable` 모두 `src/` 안 호출자 0건이고 시험에서만 호출된다. `FillObservation` 을 만드는 코드도 전부 저장된 행 재구성(replay)이며 브로커 관측에서 새로 만드는 생산자가 없다.
- 게다가 UNKNOWN 경로는 **구조적으로 닫혀 있다**: UNKNOWN 이 된 attempt 는 `order_ref` 가 `None` 인데(`lifecycle.py:476-477`) `reconcile` 의 첫 검사가 `attempt['order_ref'] == evidence.ref.to_dict()` 다(`lifecycle.py:498-517`) — `None != dict` 로 **항상 탈락**한다. `evidence_conflict` 경로도 `lifecycle.py:520` 에서 즉시 `return` 이라 증거로 풀 수 없다.
- **답이 와서 바뀌는 것**: Q9~Q12 의 취소 확정 계약이 오면 "취소 확정 뒤 재주문"을 설계할 수 있고, 그때 비로소 `reconcile` 의 제품 배선(10A2/10C)과 UNKNOWN 해제 경로를 설계한다. **증거 없이 배선만 먼저 붙이면 해제 불가능한 전면 정지를 운영에 설치하는 것**이다.

### 5-4. 답이 와도 바뀌지 않는 것

- `trading_ready` 강제 `True` 는 **금지**다. 답이 왔다는 사실이 startup 대사 구현을 대체하지 않는다.
- 모든 MODIFY 는 계속 미지원(`requests.py` 의 `prepare_modify` 가 `RequestValidationError('unsupported_modify_contract')`).
- 운영 `cancel_order`(`kis_kr.py:916-928`)가 `rt_cd=='0'` 만 보고 추적에서 주문을 지우는 것은 **main 기준의 별도 과제**이며 engine 브랜치가 고치지 않는다(시험으로 고정만 했다).
- attach 모드에 **미체결 SELL 의 시장가 에스컬레이션·미체결 BUY 의 타임아웃 취소는 여전히 없다.** 이번 조사로 그 근거가 생기지 않았다 — 보호 SELL 에 관해 attach 는 legacy 보다 계속 덜 안전하며, 이것이 attach 설치의 차단 사유다.

## ⑥ 조사의 막다른 길

**읽지 못한 1차 출처(우선순위 순)**

1. **한국투자증권 공식 Wikidocs** — 포털 `H0STCNI0` apiSummary 가 "실시간시세(웹소켓) API 사용방법에 대한 자세한 설명은 한국투자증권 Wikidocs 참고 … `https://wikidocs.net/book/7847`" 로 **직접 안내**하는 공식 교재. `wikidocs.net/170517`·`/164064`·`/239689`·`/book/7559` 모두 HTTP 403(봇 차단). 브라우저 자동화는 쓰지 않았다. **취소 확정 semantics 가 남아 있을 수 있는 가장 유력한 미확인 출처** — 필요하면 사용자 승인 아래 별도 경로로 확보할 항목.
2. **2026-09-16 `[중요] API 유량제한 적용 안내` 공지**(`…/posts/2b641ee8-b594-427a-9d11-ee6e764f0453`) — `{"message":"post.forum.read","description":"권한이 없습니다."}`. 인증 뒤 자료. 현행 유량 수치(41건/실전 18건)를 갱신했을 가능성이 있어 우선순위가 높다.
3. **공식 API 명세서 엑셀** — 2022-06-16 `API 명세서 엑셀자료 공유` 공지의 `attachFileList` 가 빈 배열이라 받지 못했다. `/api/apis/guide/excel/` 엔드포인트는 파라미터를 특정하지 못했다.
4. **로그인 뒤 Q&A(고객의소리)** — 공개 게시판 밖이라 확인 범위 밖이다.

**방법상의 한계**

- 포털의 사람용 페이지(`/apiservice-apiservice?/uapi/...`)는 SPA 라 좌측 메뉴만 돌아온다. 그래서 포털이 자기 페이지를 채울 때 쓰는 **공개 JSON 엔드포인트**(`/api/apis/public/detail?accessUrl=…`, `/api/apis/guide/property/{id}`, `/api/forums/{forumId}/posts`)를 직접 읽었다. 1차 출처 자체이지만 통상 경로는 아니므로 방법을 명시해 둔다. — 참고: `/apis/public/detail?accessUrl=/tryitout/H0STCNI0` 는 **HTTP 200 이며 `H0STCNI0` 의 res_b 26필드를 타입·길이·설명까지 준다**(이전 조사가 404 로 기록한 것은 사실이 아니다).
- `/api/forums/{forumId}/posts` 는 `sort` 없이 호출하면 HTTP 500(NullPointerException). `sort=createdDate,desc` 또는 `sort=fixOnTop,desc` 를 붙여야 목록이 나온다.
- **"FAQ 172건·공지 118건 전문을 전수 검색했다"는 표현은 이번에 재현되지 않았다.** 목록 엔드포인트의 레코드가 일부 글의 `content` 를 싣지 않는다(예: `227ac529` 레코드에 `content` 키 자체가 없다). 건수 172/118 은 맞다. **따라서 "취소 최종성·지연 상한·공통 cutoff 를 규정한 문장이 없다"는 결론은 "KIS 가 어디에도 밝힌 적 없다"가 아니라 "내가 연 문서 범위에서 없다"로 읽어야 한다.**
- API 상세의 `errorList`/`apiErrors` 는 빈 값이고, 포털 오류코드 페이지에는 취소·정정·체결 도메인 오류코드가 없다(EGW/OPSP/OPSQ 계열 게이트웨이·웹소켓 코드 위주).

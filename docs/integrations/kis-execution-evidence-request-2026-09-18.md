# KIS 최초 인계·취소/정정 체인 — 부족한 외부 증거 인수 목록

이 문서는 **추가 자료의 요청 양식**이다. 자료를 확보했다거나 거래를 허용한다는 뜻이 아니다. 현재 판정과 공식 고정 출처는 [실행 증거 계약](kis-execution-contract-2026-09-17.md)을 따른다. 합성 테스트 통과와 브로커 계약 검증을 구분한다.

## 반드시 확인할 계약

| 계약 | 공식 명세/답변에서 확인할 질문 | 증거 전 처리 |
|---|---|---|
| 현행 조회의 주문 범위 | 실전 `TTTC8001R`/`TTTC8036R`에서 원주문과 취소·정정 자식의 수량/대금은 각각 어느 주문 범위의 누적인가? 원행과 자식행을 합산하면 중복되는가? | 이름이나 수량 유사성으로 intent를 연결하지 않음 |
| 취소 최종성 | 취소 ACK 뒤 추가 체결 가능 여부, 최종 취소 확정의 필드/조합과 잔량 정의는 무엇인가? 취소가능 목록 부재로 확정할 수 있는가? | ACK/목록 부재로 원 예약을 풀거나 대체 주문을 송신하지 않음 |
| 다단 정정 | 수량 증감·가격 변경·부분체결 중 정정에서 원/자식별 목표량·체결량·잔량 관계와 주문번호 연결 규칙은 무엇인가? | 감소·매도 포함 모든 MODIFY 미지원 |
| 조회 일관성 | 여러 페이지 도중 체결이 발생할 때 중복/누락/재정렬 가능성, 페이지가 공유하는 snapshot/cursor 의미는 무엇인가? | 페이지 완결을 경제적 atomic snapshot으로 승격하지 않음 |
| 최초 잔고 인계 | 잔고와 주문/체결 조회 사이에 공유하는 cutoff/sequence 또는 명시적인 재조정 프로토콜이 있는가? 조회 지연 상한과 그 이후 완전성을 어떤 자료로 확인하는가? | 같은 잔고 반복·빈 목록·WS 연결로 startup을 열지 않음 |
| 거래소/세션 | 위 보장이 KRX/NXT/SOR·장전/정규/장후·일자 경계에 각각 적용되는가? | 입증된 조합만 지원하며 최신 TR 의미를 legacy에 자동 이식하지 않음 |

공식 답변은 대상 TR·환경·시장/세션·문서 개정일/버전과 함께 보존해야 한다. 필드 이름만 열거한 예제는 위 경제 의미의 보장이 아니다. 보장 자체가 없다면 다른 인계 설계를 별도 검토해야 하며, 현재 구현에 임의의 대기시간/반복횟수를 추가해 증명을 대신하지 않는다.

## 승인된 비식별 응답으로 보완할 경계

아래는 **이미 존재하는 승인 자료**의 인수 시나리오다. 시험용 실주문이나 실제 API 호출을 요청하지 않는다.

1. 미체결 원주문 → 취소 접수 → 최종 확정까지의 조회/통보.
2. 부분체결 → 취소와 추가 체결 경합 → 최종 수량 대사.
3. 부분체결 후 정정, 다시 정정/부분취소한 다단 체인.
4. 전체 조회 중 페이지 전환과 체결 발생; 같은 원본 식별자의 후속 조회.
5. 재시작 시 기존 보유·미체결 주문·외부/수동 주문이 함께 있는 최초 인계.
6. 지원하려는 거래소/세션별 사례와 영업일 경계를 넘는 응답.

각 시나리오는 다음을 한 묶음으로 제공한다.

- 출처·자료 사용 승인 범위·대상 TR·실전/모의 구분·거래소/세션.
- 요청 시작/응답 완료의 timezone-aware 시각과, 응답에 **실제로 존재하는** 시장/주문/체결 시각. 없는 시각은 없다고 기록한다.
- 연속조회 관련 허용 header와 요청/응답 cursor, 페이지 순서 및 실패/잘린 페이지 여부. `response: []`인 예제 파일을 실제 빈 조회로 바꾸지 않는다.
- 원주문·자식·체결·일자/조직 식별자의 일관 가명 관계; 실제 존재하는 수량·가격·대금·상태 원 필드. 필드가 없으면 새 키나 값으로 보충하지 않는다.
- 같은 범위의 잔고/미체결/누적체결 자료와, 어느 순간의 경제 상태를 의미하는지 설명하는 공식 계약 근거.

## 비식별화와 저장 경계

- API 키·secret·access/refresh token·인증 header·실계좌번호·고객정보는 받지 않는다. 원문 자격과의 mapping도 저장소에 보관하지 않는다.
- 식별자는 사례 안에서 일관된 가명을 쓴다. 체인 관계를 잃는 무작위 재치환은 인수 증거로 쓰지 않는다.
- 비식별화 과정에서 수량 보존식, 금액/수수료 차분, 페이지 연결, 시간 순서가 달라졌는지 기록한다. 변경한 숫자의 사례를 원본 실계좌 사실로 표현하지 않는다.
- 승인 전 원자료를 Git에 넣지 않는다. 승인 범위와 비밀정보 검사를 확인한 뒤 최소한의 fixture/계약 근거만 별도 리뷰한다.

## See — 자료가 왔을 때의 판정 순서

1. provenance와 허용 범위를 확인한다. 응답 샘플만으로 최대 지연·원자성 같은 전역 보장을 추정하지 않는다.
2. 현재 collector/adapter에 원 페이지를 넣어 범위·연속조회·식별자·수량을 재현한다. 정규화 가능과 최종성 지원을 따로 판정한다.
3. 실제 lifecycle → inbox → core queue → receipt/경제·보호·예약에서 보존식을 확인한다. 취소 ACK/불완전 조회에 추가 POST 0과 예약 유지 대조를 둔다.
4. 지원 계약을 좁게 등록하고 독립 리뷰한다. 정정의 경우 계약 입증 외에도 **실제 request의 추가 현금·노출·계획위험 예약**이 필요하다. BUY alpha 통과나 child attempt 추적만으로 대체하지 않는다.
5. 전체 C/F/G/R 인수와 독립 broad 리뷰 이후에만 main 통합/운영 전환을 별도 판단한다. 외부 증거가 없으면 이 목록은 미완이며 `trading_ready=False`와 미지원 체인을 유지한다.

# Bear API 400/800 진단 준비

목적은 같은 Bear 입력에서 출력 상한만 바꿨을 때 유효 의견이 끝까지 나오는지 확인할 준비를 하는 것이다. 기존 11/4 실호출의 API400은 `max_tokens`로 잘렸으며, 800에서 완료된다는 증거는 아직 없다. 선정 품질·진입 성과·순수익 비교가 아니다.

## 고정할 조건

| 항목 | 조건 |
|---|---|
| 모델·effort | `claude-opus-5-5`·`low` |
| 입력·프롬프트 | 기존 준비 자료의 공개 입력 + 기존 Bear system/suffix 그대로 |
| 비교 변수 | API 출력 상한 400 → 800 |
| 전송 | Anthropic API만, 각 1시도·총 최대 2시도·재시도 0 |
| 시한 | 각 API 시도에 고정 5.75초 |
| 비용 | 공유 월 원장, 실험 추정비 상한 USD0.50 |
| 동의 | 새 실험 ID·새 승인 창·승인자·준비 지문·고정 소스 SHA |

5.75초는 이번 API 단독 진단에 고정한 예산이다. 기존 CLI→API 흐름의 실제 잔여 시간은 CLI 종료·가드·정리 지연에 따라 달라지므로 전체 진입 경로의 성능과 동일시하지 않는다. Bull·CLI 호출과 운영 worker 활성화는 포함하지 않는다. 운영 설정·패널12/내부11.5/CLI5.75초·월USD100/`log_and_continue`·매수 중지는 바꾸지 않는다.

## 실제 원장의 선행 제약

`ComparisonCallGuard`는 월 원장 전체에 비교 정책 1개를 고정한다. 11/4 읽기 전용 확인에서 기존 `e04-acc-20261104-003490-r1` 정책(출력400·시도4·11/4 하루)이 남아 있다. 새 400/800 진단은 다른 정책이므로 현재 원장에서는 차단된다.

기존 정책을 삭제·덮어쓰기하거나, 새 월 예산 DB를 만들어 공유 상한을 분리하지 않는다. 기존 실험을 재개하거나 만료 창을 연장하지도 않는다. **이번 준비 완료만으로 실행 가능하다고 해석하면 안 된다.** 실호출 이전에 공유 월 원장을 유지하는 비교 정책 수명/분리 계약을 별도 작업으로 해결해야 하며 그 뒤 새 승인과 준비 지문을 확정한다.

## 중단과 결과 해석

첫 400 응답이 정상 완료되면 계획된 800 조건으로 이어갈 수 있다. `max_tokens` 절단도 신원·사용량·정산이 알려져 있고 다른 오류가 없으며 승인서가 그 진행 조건을 명시한 경우에만 이어간다. 부분 답변은 유효 의견으로 세지 않는다. 거절·신원 불일치·타임아웃·불명 정산·늦은 결과는 중단한다. 실패 후 새 실험이나 자동 재시도는 없다.

영수증에는 요청/응답 신원·출력 상한·stop reason·유효 판정 여부·지연·예약 정산·소유 전송 종료를 남긴다. 응답 본문·프롬프트·숨은 추론·자격증명은 넣지 않는다. 비용은 공개 가격표를 통한 추정이며 실제 청구액이 아니다.

## 준비·검증 상태

준비 진입점은 `scripts/ops/bear_api_cap_diagnostic.py`다. `prepare`는 과거 입력을 읽어 새 디렉터리에 `input.json`·`plan.json`을 작성한다. 자격증명·원장·전송을 열지 않는다. 소스 작업본이 깨끗하고 `--source-commit`과 HEAD가 일치해야 한다.

```bash
python scripts/ops/bear_api_cap_diagnostic.py prepare \
  --source-dir <기존-준비-디렉터리> --out <새-비공개-디렉터리> \
  --experiment-id <새-ID> --source-commit <고정-40자리-SHA> \
  --start <승인-제안-시작-시각+09:00> --end <승인-제안-종료-시각+09:00>
python scripts/ops/bear_api_cap_diagnostic.py check-ledger \
  --dir <새-비공개-디렉터리> --ledger-path <기존-공유-월-원장>
```

`check-ledger`는 읽기 전용 호환성 검사다. `ready`는 비교 정책 호환성만 뜻하며 사용자 승인·전체 운영 인수를 대신하지 않는다. 현재 원장은 `existing_policy_conflict`다. `run`에는 별도 승인자·승인한 계획 SHA256가 필요하고, 새 계획의 소스/입력/운영 제어/창을 검사한다. 동시·중복 소비는 거절하며 남은 창이 5.75초 미만이면 시한을 줄여 호출하지 않고 중단한다.

구현·검사 결과는 원장에 기록하며 독립 리뷰/실제 WSL 검증은 진행 상태를 구분한다. 실제 호출 승인은 없으며 실행 예약도 만들지 않는다. 최신 상태·NEXT는 [실행 원장](execution-roadmap.md#e04-bear-api-cap-prep-20261104)을 따른다.

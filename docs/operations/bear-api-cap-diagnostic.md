# Bear API 400/800 진단 준비

목적은 같은 Bear 입력에서 출력 상한만 바꿨을 때 유효 의견이 끝까지 나오는지 확인할 준비를 하는 것이다. 기존 11/4 실호출의 API400은 `max_tokens`로 잘렸으며, 800에서 완료된다는 증거는 아직 없다. 선정 품질·진입 성과·순수익 비교가 아니다.

## 고정할 조건

| 항목 | 조건 |
|---|---|
| 모델·effort | `claude-opus-5-5`·`low` |
| 입력·프롬프트 | 기존 준비 자료의 공개 입력 + 기존 Bear system/suffix 그대로 |
| 비교 변수 | API 출력 상한 400 → 800 |
| 전송 | Anthropic API만, 각 1시도·총 최대 2시도·재시도 0 |
| 시한 | 각 API 시도에 고정 5.75초 |
| 비용 | 공유 월 원장, 실험 추정비 상한 USD0.50 |
| 동의 | 새 실험 ID·새 승인 창·승인자·준비 지문·고정 소스 SHA |

5.75초는 이번 API 단독 진단에 고정한 예산이다. 기존 CLI→API 흐름의 실제 잔여 시간은 CLI 종료·가드·정리 지연에 따라 달라지므로 전체 진입 경로의 성능과 동일시하지 않는다. Bull·CLI 호출과 운영 worker 활성화는 포함하지 않는다. 운영 설정·패널12/내부11.5/CLI5.75초·월USD100/`log_and_continue`·매수 중지는 바꾸지 않는다.

## 공유 원장의 정책 등록

기존 원장의 `comparison_policy(id=1)`은 전역 한도의 불변 기준으로 남는다. 새 400/800 정책은 [정책 수명 계약](comparison-policy-lifecycle.md)에 따라 승인자·준비 지문을 갖춘 실행에서 별도 등록한다. 기존 정책이나 월 설정을 삭제·덮어쓰기하지 않는다.

`check-ledger`는 같은 정책의 기등록 상태와 새 등록이 가능한 상태를 구분한다. 지원하지 않는 구조·같은 ID 충돌·손상은 계속 차단한다. 등록 가능은 사용자 승인이나 당일 잔여 시도 수를 대신하지 않는다. 기존 전체 일 한도와 새 실험 한도를 함께 적용하므로, 11/4처럼 기존4시도가 일 한도를 모두 쓴 날에는 새 진단을 호출할 수 없다.

기존 실험 ID·만료 창·소비 표식을 재사용하지 않는다. 새 월 예산 DB로 상한을 분리하거나 기간을 자동 연장하지 않는다. 구현 및 실제 적용 상태는 원장의 E04-COMPARISON-POLICY-LIFECYCLE을 따른다.

## 중단과 결과 해석

첫 400 응답이 정상 완료되면 계획된 800 조건으로 이어갈 수 있다. `max_tokens` 절단도 신원·사용량·정산이 알려져 있고 다른 오류가 없으며 승인서가 그 진행 조건을 명시한 경우에만 이어간다. 부분 답변은 유효 의견으로 세지 않는다. 거절·신원 불일치·타임아웃·불명 정산·늦은 결과는 중단한다. 실패 후 새 실험이나 자동 재시도는 없다.

영수증에는 요청/응답 신원·출력 상한·stop reason·유효 판정 여부·지연·예약 정산·소유 전송 종료를 남긴다. 응답 본문·프롬프트·숨은 추론·자격증명은 넣지 않는다. 비용은 공개 가격표를 통한 추정이며 실제 청구액이 아니다.

## 준비·검증 상태

준비 진입점은 `scripts/ops/bear_api_cap_diagnostic.py`다. `prepare`는 과거 입력을 읽어 새 디렉터리에 `input.json`·`plan.json`을 작성한다. 자격증명·원장·전송을 열지 않는다. 소스 작업본이 깨끗하고 `--source-commit`과 HEAD가 일치해야 한다.

```bash
python scripts/ops/bear_api_cap_diagnostic.py prepare \
  --source-dir <기존-준비-디렉터리> --out <새-비공개-디렉터리> \
  --experiment-id <새-ID> --source-commit <고정-40자리-SHA> \
  --start <승인-제안-시작-시각+09:00> --end <승인-제안-종료-시각+09:00>
python scripts/ops/bear_api_cap_diagnostic.py check-ledger \
  --dir <새-비공개-디렉터리> --ledger-path <기존-공유-월-원장>
```

`check-ledger`는 읽기 전용 호환성 검사다. `ready`는 비교 정책 호환성만 뜻하며 사용자 승인·전체 운영 인수를 대신하지 않는다. `run`에는 승인자·승인한 계획 SHA256가 필요하고, 새 계획의 소스/입력/운영 제어/창을 검사한다. 동시·중복 소비는 거절하며 남은 창이 5.75초 미만이면 시한을 줄여 호출하지 않고 중단한다. 실행 디렉터리의 `consumed.json`과 정규화된 공유 원장 옆 `<원장파일명>.bear-api-cap-<sha256(실험ID)>.consumed.json` 두 소비 표식을 보존한다. 후자는 다른 폴더/프로세스의 같은 실험 ID도 차단한다. 실패·취소·종료 후 표식을 삭제해 재실행하지 않는다. 현재 작업에서는 실제 원장의 표식을 만들지 않았다.

구현과 AWS 보조 관련 검사176건(신규40건), 독립 Codex Astra/xhigh 재리뷰(최초P2 2건 반영, 최종P0/P1/P2 0)를 마쳤다. 같은 제공자 독립 리뷰이며 교차 제공자 리뷰로 부르지 않는다. 실제 사용자 WSL의 최종 `c74071d7` 직렬 전체는 10,442 passed / 2 skipped / 2 xfailed·rc0·격리0, 작업본/원본 보존과 로그 해시 일치를 확인했다. 최초 PR CI에서 코어 지표 테스트의 현지 시각 의존성을 발견해 고정 시각 재현 후 테스트만 수정했으며, 최초 WSL 통과·CI 실패 기록도 보존한다. 완료된 기존 WSL/CI를 반복한 결과가 아니다. 이 문단의 검증 수치는 PR336 당시 준비 단위의 이력이다. 후속 정책 수명·새 실호출 승인의 현재 상태와 NEXT는 [실행 원장](execution-roadmap.md#e04-comparison-policy-lifecycle-20261104)을 따른다.

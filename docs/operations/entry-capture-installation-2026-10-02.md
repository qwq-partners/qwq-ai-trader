# 2026-10-02 첫 후보 관측 설치안 — 검토용, 미실행

> 사용자가26차 실행 범위를 승인했다. 실제 준비·설치·예약 상태는 [실행 기록](capture-execution-2026-10-02.md)을 따른다. 아래는 승인받은25차 설계다.

목적은 현재 엔진의 후보 선정·진입 강점을 실제 수신 자료로 검증하고, **같은 종목·같은 수량에서 비용 후 진입 가격 조건을 개선할 수 있는지** 확인하는 것이다. 매수 중지를 유지한다. 관측 코드는 주문 차단기가 아니므로 기존 청산 관리와 거래 안전장치를 그대로 보존한다. 한 번의 관측은 자료 품질 점검이며 수익성 입증이나 최적 시간대 선정이 아니다.

검토 입력은 [고정 입력 제안 JSON](../research/current-engine-capture-proposal-2026-10-02.json)에 있다. study·시작 요청·토스 v2 plan·소스 지문과 예산을 채웠고, 실제 계정 신원/승인/grant/배포 지문은 빈 값으로 남겼다. 이 문서나 JSON은 실행 승인서가 아니다. 기존 [첫 수집 초안](../research/current-engine-first-capture-draft-2026-10-01.json)의 10시 일정은 이번 제안으로 대체하되 과거 근거는 보존한다.

## 실제 적용 전 확인할 입력

아래는 아직 실행하지 않은 운영 점검이다. 현재 요청의 명시 승인 뒤에만 읽으며 출력은 허용된 비밀 아닌 값으로 제한한다.

- 봇/퇴역 토스 서비스의 상태, 실제 실행 사용자·그룹, 작업 디렉터리와 시작 인자의 허용 목록(config·market·dry-run·관측 옵션 존재). 전체 환경/명령행/로그를 출력하지 않는다.
- 운영 기본 설정 SHA와 override SHA가 제안 JSON과 같은지, KR 매수 중지 유지 여부. 운영 gap 배분은 디스크 기준5%, 작업본은15%다. 작업본 override를 복사하거나 배분을 늘리지 않는다. 기록된0.7% 위험·18% 종목 한도는 연구 선언이며 실행 중 메모리 설정의 인증이 아니다.
- 기존 토스 서비스 UID/GID·host와 정확한 비밀 아닌 client identity, 단일 발급 주체/기존 발급 시도 및 sender 소유권. 자격증명 값/토큰 내용은 읽거나 보고하지 않는다. 기존 발급 안전 기록으로 새 연결이 허용되지 않으면 중단한다.
- 현재 메모리/디스크 여유, 이미 노출된 내부 WS 등록·유량 요약만 확인한다. 사용자 확인상 외부 WS 예약은0이다. `operational_headroom=4`는 새로 선언한 보수적 예약량이며 실측 잔여 채널 수가 아니다. 실제 등록 한도41·최대후보3 검사는 기존 조정기가 유지한다.
- 검토·통합한 엔진 release와 토스 immutable artifact의 정확한 지문, 명시 offline wheelhouse. 이번 소스 manifest는 로컬 작업본262개 Python 파일 지문이며 운영 실행 코드 증명이 아니다. 코드가 달라지면 study/source/plan/grant 지문을 함께 다시 고정한다.
- 당일 일반주식 대상·공개 KRX 비용표·실제 세션 증거. ETF/ETN/NXT 값을 기존 KRX 일반주식 비용 모형에 넣지 않는다. 해당 증거가 없는 후보는 수익 계산에서 unknown이다.

## 설치 범위와 순서

1. **준비:** 현재 요청의 운영 변경/재시작/토큰 사용/한정 관측 승인을 기록한 뒤 위 점검을 완료한다. 운영 설정·KR 매수 중지·기존 인증 기록·이전 cohort를 보존한다. 검토된 소스로 엔진 통합 release를 정하고, 명시 wheelhouse를 사용하는 기존 패키저로 토스 artifact를 오프라인 작성·검증한다. 자격증명이나 실행 상태는 artifact/커밋에 넣지 않는다.
2. **엔진 입력:** 제안 JSON의 `study`, `engine_manifest`, `once_request` 객체를 명시된 직렬화 방식으로 각각 `study.json`, `manifest.json`, `once.json`에 쓴다. 목적지는 제안의 `engine_inputs`이고 runtime UID 소유 비공개 디렉터리0700·파일0600이다. `engine_state`도 같은 UID의 새0700 디렉터리로 만들되 `startup.receipt`와 `engine.jsonl`은 미리 만들지 않는다. 입력의 study/raw hash를 대조한다. 기존 원장이나 영수증을 삭제해 재시도하지 않는다.
3. **토스 새 cohort:** 기존 `/var/lib/qwq-toss-observer/tokens`, `sender.lock`, `starts`와 과거 cohort를 보존한다. 새 plan canonical SHA를 이름으로 쓰는 cohort만 서비스 UID 소유0700으로 만든다. 이전 `install.py`는 v1·3일 신규 설치 전용이며 재설치/업데이트에 사용하지 않는다. 과거09/17 승인 참조를 새 WS 승인으로 복사하지 않는다.
4. **v2 입력 결합:** `grant_review_fields`의 빈 필드는 새 승인·기존 실제 identity·검토 artifact로 채운다. schema2 grant에 query/renewal/bootstrap/websocket을 명시하고08:55~09:46만 허용한다. bootstrap 허용은 기존 소비 기록을 초기화하지 않는다. deployment는 실제 service UID/GID·root-owned plan/registry 경로·release manifest·artifact/config hash·새 ledger·기존 token/sender/start 경로를 결합한다. `retention_at=expires_at+30일`을 유지한다. `status_path`는 스키마 호환 필드일 뿐 WS 서비스는 그 파일을 쓰지 않는다.
5. **정지 상태에서 교체:** 퇴역 토스 서비스가 비활성인지 확인하고 새 artifact를 root 소유의 새 immutable release 경로에 stage한다. root-owned launcher·plan·registry·deployment의 이전 비밀 아닌 파일을 제한된 위치에 백업한다. 새 파일 각각의 지문/소유권을 확인하고 **서비스가 비활성인 동안만** 일치하는 세트로 교체한다. 파일 검증/교체는08:55 전에 마친다. `launcher --check`는 실제 grant를 읽고 현재 시간을 검사하므로 **08:55 이후**에 실행한다. 이 점검과 승인/배치 검증이 모두 통과한 뒤08:57 전에만 기동한다. 승인 시작 전의 실패를 재발급/권한 확대로 해결하지 않는다. 여러 파일의 교체를 단일 원자적 작업이라고 표현하지 않는다. 실패하면 이전 파일로 복원하되 만료된 옛 관측 서비스는 기동하지 않는다.
6. **봇 기동:** 운영 시작 명령의 config/market 등 기존 값을 보존하고 `--entry-observation-once <engine_inputs>/once.json`만 추가한다. 장전08:55~08:57 안에서 한 번 재시작한다. selector가 영수증을 배타적으로 만들고 파일·부모 디렉터리를 동기화한 뒤 study를 검증한다. 이후 실패도 시도 소비다. 잘못된 요청 파일은 기동 오류이므로 기동 전 소유권·경로·시간·study 검증을 마친다. 관측 설치 실패 시 새 관측 인자만 제거해 검토된 보통 시작 경로로 복구할 수 있으며 KR 매수 중지는 유지한다. 반복 실패나 장 개장 이후에는 자동 재시작 반복을 중단한다.
7. **한 번 수집:** 기존 서비스 hardening·네트워크 제한을 유지하고 명시 승인된 토스 서비스 시작1회만 수행한다. root-owned 경로 검증과 신규 시작 영수증 확인이 선행한다. 수집기는 첫 후보를 받아 단일 연결·고정3종목 구독한다. 토스 단독 오류에는 관측 서비스만 중단하며 봇을 재시작하지 않는다. 엔진 관측·loopback 준비가 되지 않았으면 시작하지 않는다.
8. **종료 확인:** 토스 종료코드0·최종 봉인 결과의 `service_complete`·종료 사유·엔진 원장 봉인을 함께 본다. WS에서는 과거 REST `status.json` 계수를 기다리지 않는다. 같은 grant/file로 재시작하지 않으며 auto-enable/timer로 다음 날 수집하지 않는다. 사용한 봇 1회 옵션은 소비됨/기간 밖이면 일반 시작으로 돌아가지만 요청 파일 자체의 손상은 오류가 될 수 있어 파일을 보존한다.

이 순서는 현재 metadata/새 승인/artifact가 결합된 최종 실행 명령을 만들기 위한 고정 절차다. 아직 root 파일·unit·서비스·운영 코드에 적용하지 않았고 배포 지문이나 실제 UID를 추정하지 않았다. 운영 metadata가 다르면 임의로 넓히지 않고 불일치를 해결한 입력을 다시 검토한다.

## 수집 후 바로 할 일

엔진 원본 JSONL과 study hash/capture ID/source sequence를 대조하고, 토스 최종 파일을 기대 plan hash로 읽는다. 전체 반환 수·관측3개·미관측 수, signal/order_ready 도달 수와 결측 원인을 먼저 기록한다. 서비스가 정상 종료됐어도 LOSSY 무손실이나 호가 확보를 뜻하지 않는다. 상한은 엔진5만 기록/64MiB·토스1만 프레임/16MiB이며 장중 유량 충분성은 아직 확인되지 않았다. 강제 종료 시 토스 중간 호가는 복구하지 못한다.

KIS 최초 ask와900초 후 최초 bid가 유효한 동일 수량 후보에만 A(기존 진입)와 B(비용 반영 가격 조건)를 대조한다. 공개 KRX 비용 기준·추가 슬리피지0/양방향10/30bp 결과를 모두 보고하고 피한 손실·놓친 이익·unknown 비율을 함께 본다. 그다음 독립 기간에서 반복하고, 체결/청산/현금 재사용·AI/자료/서버 비용·전체 KODEX200 기회비용까지 포함해 계좌 순수익을 확인한다. 반도체 제외군·버전·상승/하락장 구분은 보조 진단으로 유지한다.

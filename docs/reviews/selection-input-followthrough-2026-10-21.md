# 기존 자료로 진행하는 종목 선정 입력 수정

## 목적과 사용자 결정

목적은 종목 선정과 진입·청산 판단의 오류를 줄여 비용 후 순수익을 개선하는 것이다.
사용자는 10월21일 가상 초기자금 1,000만원과 모의투자 제안을 철회했다.
실제 현금 부족은 자금 제약이며, 이를 해결하려고 현금 조건이나 매수 중지를 바꾸지 않는다.
새 진입 체결이 없어도 재현할 수 있는 입력 전달 오류부터 수정한다.

이 변경은 개발 작업 트리에만 적용한다. 운영 `84fc2b3a`, 실계좌/보유 상태,
10월22일 고정 관측·판독 입력과 월 USD100 예산은 변경 대상이 아니다.
운영 배포 전 고정 관측과의 충돌을 별도로 확인해야 한다.

## PLAN — 확인된 오류와 우선순위

1. **상위 후보의 변동성 검사 누락.** 모멘텀 단계는 처음 상위20개에 30일 일봉을
   저장한다. 거래량 보완 단계는 그 밖의 후보에 5일만 저장한다. 이후 섹터 보정으로
   상위20에 올라온 후보는 변동성 단계가 그 5일 캐시를 그대로 사용하면서
   `len < 20`에서 빠진다. `atr_pct=None`은 스케줄러의 기존 4% 대체값으로 이어져,
   실제 자료로 계산할 수 있었던 ATR 감점과 10% 초과 차단을 놓칠 수 있다.
2. **배치 판단 지표의 대기·재시작 경계 유실.** Swing 후보의 수급·LCI·날짜 정렬
   MRS는 기술지표 캐시의 복사본에 추가된다. 전략 Signal에는 있지만 PendingSignal은
   값 대신 키 목록만 저장한다. 실행 시 공용 캐시를 다시 읽으면 보강된 값과
   명시적 0/미관측 구분이 사라진다. 판단 당시 값과 원래 시각을 함께 전달해야 한다.
3. **API 효율은 기존 계측으로 먼저 판별.** 잔고/포지션의 중복 조회는 이미 캐시를
   사용한다. 요청량만 보고 속도나 재시도를 바꾸거나, 근거가 없는 당일 캐시를 추가하지 않는다.

## DO — 수정 범위

### 거래량과 ATR의 공유 일봉

- 거래량 보완의 캐시 미스 요청을 5일에서 뒤 변동성 단계와 같은 30일로 맞춘다.
- 점수·ATR 임계값·후보 상위20 제한·스캔 간 캐시 수명은 유지한다.
- 30행을 한 번에 반환하는 응답은 기존과 같은 HTTP 1회다. 이미 충분한 캐시가 있으면
  추가 HTTP는 없다. 실제 상장 이력이 짧거나 공급자가 적은 행만 반환하면 기존 브로커의
  페이지네이션이 추가 요청을 할 수 있으므로 모든 경우의 호출 수 불변을 주장하지 않는다.
- 실제 자료가 20행 미만이면 ATR 미관측을 유지한다. 이 변경으로 기존 ATR 4% 대체 정책까지
  정당화하거나 변경하지 않는다.

### 배치 판단 지표

판단 당시 스냅샷을 대기 신호 저장·복원·실행까지 보존한다. 원래 지표 시각을 현재 시각으로
바꾸지 않는다. 새 형식의 손상 자료와 스냅샷 없는 과거 자료를 구분하며, 새 스냅샷이 손상됐을 때
공용 캐시로 조용히 대체하지 않는다.

- `inputs_ref.indicator_snapshot` 버전1에 지표와 원래 시각을 깊은 복사로 저장한다.
  실행 신호는 이를 `pending_snapshot` 출처로 사용한다.
- VCP 생산자도 SEPA·RSI2와 같이 후보 원 지표를 신호에 전달한다. 세 생산자와
  LLM 점수 재정렬 뒤 메타데이터 보존 경로를 확인했다.
- 과거 JSON에 스냅샷이 없을 때만 기존 캐시를 `legacy_cache` 출처로 사용한다.
  과거 계획의 시각을 현재 캐시 값에 붙이지 않고 실제 캐시 시각이 없으면 `None`으로 남긴다.
- 새 스냅샷 형식·버전·시각이 손상되면 `invalid_snapshot`과 빈 지표를 전달한다.
  이것이 별도의 신규 거래 차단 정책은 아니며, 기존 소비자의 결측 처리 규칙은 유지한다.
- 수급의 공급자 기준일·수신 시각은 개별 근거 안에 보존한다. 전체 지표의 계산 시각을
  모든 개별 입력의 최신성이나 공급자 관측 시각으로 해석하지 않는다.
- 과거 JSON에서 이미 없어진 정보는 복원하지 않는다. 별도 시세 조회나 새 신선도 기준,
  주문·사이징·청산·현금 정책은 추가하지 않는다.

## SEE — 재현과 검증

- ATR 수정 전: 실제 `KISBroker.get_daily_prices`와 가짜 HTTP 응답을 연결한 시험에서
  21위→상위20 후보의 ATR이 `None`으로 남는 실패를 재현했다(1 failed / 2 passed).
- 수정 후: 같은 입력에서 ATR12%, 기존 규칙의 -15점이 적용된다. 30행 응답의 HTTP1회,
  충분한 기존 캐시의 HTTP0회, 실제 5행 이력의 ATR 미관측도 함께 확인했다.
- 선정 관련 시험139 passed, 운영 상태·외부 네트워크 접근 시도0.
- 배치 입력 초기 회귀12건의 실패를 재현했다. 실제 기술지표→Swing 보강→SEPA 신호→
  원자적 JSON 저장→새 분석기 실행 경로, 명시적0/None·원래 시각·구형/손상 자료를 검증했다.
  새로운 배치 회귀20건을 포함한 최종 통합 관련 시험281 passed, rc0, 격리 위반0.
  기존 메타데이터 허용 키 검사는 출처·시각 두 키만 추가하고 필수 키·값 검증을 유지했다.
- 독립 중요 재리뷰 승인, 남은 P0/P1/P2 지적0. 리뷰어의 최종 관련32건과 실제 VCP 소비자
  독립 재현도 통과했다(rc0, 격리 위반0). 요청 모델/effort는 Astra/xhigh이며 실제 실행
  모델·effort 메타데이터는 미노출로 미검증이다. 구현 요청은 Astra/high, 원인 분석은 Sol/high였다.
- 최종 전체 `scripts/dev/verify.sh`: **8,551 passed / 2 skipped / 2 xfailed**, rc0,
  696.54초. 전체 Python 구문·비밀정보 의심 패턴 검사 통과, 운영 상태·외부 네트워크
  접근 시도0. 비공개 실행 로그는 `~/.local/state/qwq-selection-followthrough-20261021/`
  아래 `full-verify-final.log`이며 저장소에 포함하지 않는다.
- 독립 리뷰에서 VCP 생산자의 지표 누락을 추가 발견했다. 스냅샷을 항상 생성하는 초기
  수정은 VCP에 빈 지표를 전달해 추격 감점을 잃을 수 있었다(같은 합성 입력에서49점 차단→
  64점 통과 재현). 전체 검증 첫 실행은 이 지적을 반영하기 위해 중단했으며 성공으로 세지 않는다.
  VCP 생산 경로를 보완한 뒤 원래49점 차단을 확인했고, 원시각·실제 소비자까지 회귀 검증했다.

## 기존 API 집계의 의미

새 API 호출 없이 10월21일 배포 전 저장된 health의 프로세스 누적 계수를 읽었다.
개별 요청 시각별 집계나 현재 운영 계수는 아니다.

| 경로 | 저장된 집계 | 판단 |
|---|---|---|
| 포트폴리오 동기화의 포지션 조회 | 689회 전부 캐시 적중 | 잔고 중복 조회를 다시 수정할 근거 없음 |
| 일봉 조회 | HTTP3,150회, EGW00201 136회 | 반복 조회·호출 제한은 남아 있으나 개별 호출 원인은 미귀속 |
| 동기화 잔고 조회 | HTTP779회, EGW00215 89회 | 원장 한도 문제를 일반 시세 호출 탓으로 단정하지 않음 |
| 직접 재무 조회 | HTTP477회, HTTP오류23회 | non-200 오류 코드가 없어 EGW라고 단정하지 않음 |

브로커·시장자료·스크리너는 프로세스 공용 리미터를 사용한다. 외부 프로세스와의 공유는
없다. 직접 GET의 거절 피드백과 반복 전일 거래량 조회는 별도 개선 후보지만, 이번 선정
정확성 수정과 함께 전역 호출 정책·캐시 신선도 정책을 바꾸지 않는다.

## 수익성과 다음 순서

위 시험은 실제 코드에서 입력 누락을 고친 근거다. 실거래 체결, 순수익 향상이나 새 전략의
우위를 입증한 결과가 아니다. 모의 계좌·가상 체결·가상 수익률은 만들지 않는다.

1. 두 입력 수정의 개발·통합 검증·중요 리뷰는 완료했다. 문서와 함께 커밋·푸시하며
   PR 필수 CI·병합 상태는 해당 GitHub 영수증을 따른다. 운영 적용과는 별도다.
2. 10월22일 기존 관측을 판독해 실제 후보의 판단 근거와 이후 가격을 비교한다.
   가격 변화는 실현 손익과 분리하고, 결측 때문에 가능한 분석까지 중단하지 않는다.
   고정 관측 종료·봉인을 확인한 뒤 이번 수정의 운영 반영을 검토한다. 이 작업에서
   배포·재시작을 실행하거나 기존 예약의 소스 지문을 새 버전으로 바꾸지 않는다.
3. 청산은 이미 있는 실제 진입·가격 경로·당시 설정이 충족되는 사례에서 기존 첫 청산
   도구를 사용한다. 새 진입/체결이 필요한 검증은 자료가 생길 때 진행한다.
4. 반복 API 호출 개선은 성공한 자료의 재사용 범위와 정정 가능성을 정한 한정 변경으로
   검토한다. 원인 없이 호출 제한을 더 낮추거나 보유 관리 빈도를 줄이지 않는다.
